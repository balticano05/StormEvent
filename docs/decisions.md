# Журнал архитектурных решений (ADR)

Канонический реестр решений проекта StormEvent. Каждое решение карточкой: **дата · контекст · решение · последствия · статус**.
Источники: [`25_contradictions.md`](25_contradictions.md) (27 противоречий ПРОТ-01…27 и ответы владельца), [`24_implementation_plan.md`](24_implementation_plan.md) (ФАЗА 0, шаги 5–40 + блок 40.1).

## Как читать номера

| Серия | Что это | Статус |
|---|---|---|
| `ADR-001…ADR-016` | Базовые технические решения ФАЗЫ 0 (БД, доступ, миграции, очередь, клиенты, LLM, TZ) | принято |
| `ADR-VL-01…ADR-VL-14` | **Решения владельца** (канон; помечены в плане как `[ВЛ]`, спорить не нужно) | принято |
| `ADR-017…ADR-052` | Черновики «на ходу» внутри шагов плана (напр. `NamedParameterJdbcTemplate`, `jsonb`) | не канон — в реестр попадут при реализации |

Легенда статусов: **принято** · **действует** · **заменено** ( ссылка на замену) · **отменено** ( ссылка на ПРОТ/ADR).

Правило: изменение любого принятого решения = новая карточка со статусом «заменено» у старой. Решения владельца меняются только новым решением владельца.

## Базовые решения

### ADR-001
**База данных — PostgreSQL 16** · принято · 2026-09-26

- **Контекст:** нужны реляционные данные (сессии, кэш, состояния источников, логи, агрегаты метрик), TTL-чистки, индексы, транзакции сессий.
- **Решение:** PostgreSQL 16, поднимается через Docker Compose (`compose.yml`, `localhost:5432`). Схема `storm`.
- **Последствия:** нужны `spring-boot-starter-jdbc`, драйвер `postgresql`, `flyway-core`. Миграции — единственный способ менять схему.
- **Альтернативы:** H2 — только тесты; Redis — не берём (ADR-005), KV-хранилище не даёт агрегаций по метрикам.

### ADR-002
**Доступ к БД — Spring Data JDBC + JdbcTemplate, без JPA** · принято

- **Контекст:** доменная модель (`Offer` и сущности источников) не является картой таблиц; JPA-магия мешает тонкому контролю SQL.
- **Решение:** `NamedParameterJdbcTemplate` (безопасно по SQL-инъекциям) + репозитории в пакете `repository`; в сервисах SQL не пишем.
- **Последствия:** больше ручного маппинга, предсказуемые планы запросов; unit-тесты на репозитории — с H2.

### ADR-003
**Миграции — Flyway** · принято

- **Контекст:** несколько разработчиков и окружений, нужен единый источник правок схемы.
- **Решение:** `flyway-core`, версии `V1…Vnn`; ручной `ALTER` запрещён (ADR-040).
- **Последствия:** схема в репозитории; в тестах Flyway либо отключается, либо работает на H2 в PostgreSQL-режиме.

### ADR-004
**Тестовая БД — H2 в PostgreSQL-режиме** · принято

- **Контекст:** тесты должны идти без Docker.
- **Решение:** H2 (`MODE=PostgreSQL`) для юнит/интеграционных; `Testcontainers` — опционально для pg-специфики (партиционирование, jsonb).
- **Последствия:** если jsonb мешает — маппинг через `JsonNode` из `TEXT` (черновик «ADR-028» в плане).

### ADR-005
**Кэш и сессии поверх Postgres, без Redis** · принято

- **Контекст:** ПРОТ-18 — лишняя инфраструктура ради MVP.
- **Решение:** таблицы `cached_result`, `session`, `session_message`; in-memory кэш как ускоритель, но не источник истины.
- **Последствия:** сессии переживают рестарт; кэш общий для всех инстансов; нужны housekeeper-задачи.

### ADR-006
**Очередь запросов — `ArrayBlockingQueue(100)`, FIFO** · принято

- **Контекст:** ПРОТ-05, У-6 — в доках были `PriorityBlockingQueue` + aging + ramp-up.
- **Решение:** один in-memory FIFO-очередь на 100 задач, 4–8 воркеров, дедупликация по `requestId`; аудит в `request_log`.
- **Последствия:** порядок обработки = порядок поступления; переполнение → 503 + `Retry-After: 5` (ADR-VL-05). Распределённой очереди нет — архитектура single-node (черновик «ADR-045»).

### ADR-007
**Схема пакетов — по блюпринту 23, circuit исключить** · принято

- **Контекст:** ПРОТ-08/09 — circuit breaker вычеркнут из MVP.
- **Решение:** `gateway/normalize/orchestration/agent/cache/session/queue/scheduler/exception/web/handler/metrics`; пакета `circuit` нет.
- **Последствия:** быстрый сбой источника — только по `source_state.enabled`/`draining`; спека breaker'а остаётся в `16` и `23` как материал для будущей задачи.

### ADR-008
**HTTP-клиенты — базовый + производные `newBuilder()`** · принято

- **Контекст:** ПРОТ-03 — в блюпринте был «единственный клиент, пул 5», из-за чего тяжёлые POST (BZD, TicketBus) блокировали лёгкие.
- **Решение:** несколько `OkHttpClient` разрешены: базовый + производные с per-source таймаутами/пулами, отдельный профиль для SSE.
- **Последствия:** `OkHttpProperties` расширяется overrides'ами вида `source-*.timeout-ms`; таймауты задаются явно (никаких «бесконечных» `callTimeout=0`).

### ADR-009
**Fan-out к источникам — виртуальные потоки Java 21** · принято

- **Контекст:** параллельный опрос 5 источников на каждый запрос.
- **Решение:** `Thread.ofVirtual().name("src-<source>")`, без пула на источник; MDC пробрасывается в дочерние потоки.
- **Последствия:** дёшево создавать задачу на источник; ограничитель — таймауты и semaphores на тяжёлых источниках.

### ADR-010
**Общий deadline 15 с с отменой незавершённых задач** · **ОТМЕНЕНО**

- **Контекст:** в плане была deadline-модель с бюджетом 90 % и `future.cancel(true)`.
- **Решение владельца:** общего дедлайна нет — **ждём все источники**; `deadlineMs` — advisory; таймауты per-source; отмены нет (ПРОТ-01/02, У-6, У-7).
- **Последствия:** см. [ADR-VL-03](#adr-vl-03) и [ADR-VL-09](#adr-vl-09); тесты «TIMEOUT к deadline» и `ParallelFactorCancelTest` сняты.

### ADR-011
**`requestId` генерируется на входе** · принято

- **Контекст:** нужна сквозная трассировка HTTP → инструмент → источник → парсер → ответ.
- **Решение:** `RequestIdFilter` кладёт `requestId` в MDC и в `request_log`/`source_error_log`; заголовок запроса используется, если присутствует.
- **Последствия:** пользовательские сообщения об ошибках не содержат JSON-конверта, но `requestId` всегда в логах (ADR-VL-01).

### ADR-012
**LLM за интерфейсом `LlmGateway`, провайдер — OpenRouter** · принято

- **Контекст:** У-4, В-9 — нужен реальный LLM с function calling; ключ появится позже.
- **Решение:** интерфейс `LlmGateway` (agentic-режим: `nextTools(...)` + `complete(...)`); конфиг из `OPENROUTER_API_KEY` / `OPENROUTER_MODEL`; при отсутствии ключа — fallback без LLM.
- **Последствия:** смена провайдера не трогает агент; тесты LLM — на моках; `RuleBasedFallback` живёт параллельно.

### ADR-013
**Порядок фаз реализации** · принято

- **Решение:** БД → исключения → модель → гейтвеи → параллельность → инструменты → combiner → LLM → web → очередь/сессии/кэш → метрики → E2E. Circuit breaker не делаем.
- **Последствия:** каждая фаза заканчивается зелёными тестами и карточкой в этом реестре.

### ADR-014
**Именование таблиц snake_case; PK — `bigint identity` или UUID** · принято

- **Решение:** ссылки между таблицами — UUID (`session_id`, `request_id`); суррогатные логи — `bigint identity`.
- **Последствия:** естественные ключи для состояний источников — имя источника (черновик «ADR-031»).

### ADR-015
**Идентификаторы сущностей источников — `source:kind:externalId`** · принято

- **Решение:** строковые id вида `atlasbus:ride:12345`, в БД `varchar(128)` с уникальным индексом.
- **Последствия:** дедупликация между источниками возможна; id переживает смену БД.

### ADR-016
**Временные зоны — Europe/Minsk** · принято · ПРОТ-15

- **Контекст:** расчёты, стыковки, границы суток и отображение для пользователя из РБ.
- **Решение:** все расчёты и отображение в `Europe/Minsk`; в БД `timestamptz` (технически UTC), API отдаёт `+03:00`.
- **Последствия:** агрегаты метрик считаются по UTC-часам (черновик «ADR-035»), пользовательские границы суток — по Минску.

## Решения владельца (канон)

> Помечены в плане как `[ВЛ]`, в доках — как `[ВЛ]`/`[ОТМЕНЕНО]`. Основание: ответы владельца по противоречиям ПРОТ-01…27 и вопросам У-1…У-8 / В-1…В-15 (`25_contradictions.md`, разделы 0, 0.1, 0.2).

### ADR-VL-01
**Текстовый контракт: один чат-эндпоинт, ответ `text/plain`** · принято

- **Контекст:** ПРОТ-13/16/17 — в доках был JSON `SearchResponse`/`ResponseDto`/`openapi.yml` и три эндпоинта (`search`, `refine`, `sessions/{id}`); У-1, В-7.
- **Решение:** `POST /api/v1/agent/chat`, вход `{sessionId?, text}`, ответ — **строка** `text/plain`. Отдельных `search`/`refine` и структурированного JSON нет. SSE наружу не отдаём.
- **Последствия:** проще клиент и фронт; теряем машинную интеграцию (когда понадобится — отдельное решение). Ошибки источников передаются в тексте, а не кодом ответа.

### ADR-VL-02
**Сессия-чат в Postgres, TTL 15 минут** · принято

- **Контекст:** ПРОТ-06/07 — расходились TTL 30/60 мин и 15 мин idle, `session_refine` против истории диалога; У-2.
- **Решение:** сессия = диалог; таблица `session_message` (роль/текст/время/`requestId`); TTL **15 мин** с последнего обращения; состояния `NEW|ACTIVE|EXPIRED` (без `CANCELLED`).
- **Последствия:** `session_refine` не делаем; контекст для LLM = последние 20 сообщений; истёкшая сессия → `SESSION_EXPIRED` и новый `sessionId`.

### ADR-VL-03
**Агентный цикл: LLM выбирает инструменты, мы ждём все источники** · принято

- **Контекст:** ПРОТ-14/22; В-11/В-12/В-13; раздел 0.2.
- **Решение:** OpenRouter function calling: LLM возвращает `tool_calls` → инструменты-источники выполняются **параллельно** → fan-in **ждёт все** → результаты (`{status, offers|error}`) возвращаются в LLM → повтор до `maxToolRounds` → финальный текст. Контекст — вся сессия, максимум 20 сообщений. Лимит раундов — на уровне агента (`AgentProperties.llm.maxToolRounds`, по умолчанию 2 + правило в системном промпте; жёсткой остановки в коде нет).
- **Последствия:** фиксированного маппинга «интент → инструмент» нет, `forceSource` отменён; до появления ключа работает fallback-решатель с тем же интерфейсом; позже так же настроим для n8n.

### ADR-VL-04
**Circuit breaker отложен** · принято

- **Контекст:** ПРОТ-08…12, В-8 — в доках был breaker (5 ошибок/30 с → OPEN на 60 с, HALF_OPEN, `circuit_state`, `pausedUntil`, метрика `source.circuit`).
- **Решение:** в MVP **не делаем**: ни состояний CLOSED/OPEN/HALF_OPEN, ни таблицы `circuit_state`, ни проб, ни пауз. Вместо: per-source таймауты, алерт по счётчику ошибок, ручной флаг `source_state.enabled` (+`draining`) с `X-Api-Key`.
- **Последствия:** источник не «отключается» сам — падает, упоминается в тексте, деградация видна в метриках и алертах; оператор решает вручную. Спека breaker'а сохранена в `16_unhappy_circuit_switch.md` и `23_impl_blueprint.md` как материал для будущей задачи.

### ADR-VL-05
**Очередь простая: FIFO, без приоритетов и aging** · принято

- **Контекст:** ПРОТ-05, ПРОТ-12, У-6 — в доках были `PriorityBlockingQueue`, aging, `pausedUntil`/cooldown, приоритет refine-запросов.
- **Решение:** `ArrayBlockingQueue(100)`, FIFO, 4–8 воркеров, дедупликация по `requestId`; переполнение → **503** `QUEUE_REJECTED` + `Retry-After: 5`.
- **Последствия:** нет «счастливых» пользователей при перегрузке — честный FIFO; поля `priority` в контракте нет.

### ADR-VL-06
**Наблюдаемость: без Prometheus/actuator, свои счётчики + алерты** · принято

- **Контекст:** ПРОТ-20/21 — в плане был `/actuator/prometheus` и Grafana.
- **Решение:** Prometheus и actuator не подключаем; счётчики в памяти (`MetricsCollector`) + `AlertEvaluator` с логом WARN/ERROR (пороги в конфиге), имена метрик — по единому словарю.
- **Последствия:** выгрузка метрик во внешнюю систему — отдельное решение позже; сейчас хватает логов и алертов.

### ADR-VL-07
**Ошибки источников: 403 без retry, один запрос = одна ошибка** · принято

- **Контекст:** ПРОТ-04/10/11 — в доках 403 открывал circuit и запускал бесконечный retry; ошибки источника терялись в partial.
- **Решение:** `403` → сообщение пользователю **без повторов**; `401` → **один** warmup-retry; `429`/`503` → ошибка сразу, **без retry и без пауз**; `retry` одного логического запроса = **одна** ошибка в метриках; упавший источник **всегда** упоминается в тексте ответа.
- **Последствия:** метрика ошибок не раздувается ретраями; пользователь всегда видит, какие источники не ответили.

### ADR-VL-08
**Модель оффера: цены и тарифы подробно, остальное минимум** · принято

- **Контекст:** ПРОТ-19, В-10 — в модели были избыточные поля, в другом доке — минимум без тарифов.
- **Решение:** подробно — цены и тарифы (`price` + `currency`, `tariffName`/`class`, `seats`); минимум — `from`, `to`, дата/время, `source`, `kind`, `url`/`externalId`. `attributes`, `baggage`, `documents`, `cancellation`, `transfers` — после MVP.
- **Последствия:** `Offer` компактный и достаточный для MVP; детальные тарифы отдельными полями, а не в `attributes`.

### ADR-VL-09
**Отмена запроса пользователем не делается** · принято

- **Контекст:** У-7 — в плане были `CANCELLED`, `AbortController`, отмена задач и SSE-потоков.
- **Решение:** пользователь не может отменить запрос; состояния `CANCELLED` нет.
- **Последствия:** fan-in всегда доводит до конца (ограничен таймаутами); тесты отмены сняты; «убийство» потоков по флагу отключения источника не делаем (только `draining`).

### ADR-VL-10
**Админка и диагностика — за `X-Api-Key`** · принято

- **Контекст:** ПРОТ-26 — эндпоинты управления источниками были без защиты.
- **Решение:** `/api/v1/sources/**` и `/api/v1/diagnostics/**` требуют заголовок `X-Api-Key` со значением из `STORM_ADMIN_KEY` + CORS-whitelist.
- **Последствия:** секьюрти конфигом, без ролей; в тестах — заглушка фильтра; секрет только в env.

### ADR-VL-11
**Обход anti-bot не делаем** · принято

- **Контекст:** ПРОТ-27 — в доках были headless, «реалистичный fingerprint», residential proxy.
- **Решение:** уважаем `robots.txt`; при капче/Cloudflare — сообщение пользователю + алерт, источник отключается вручную.
- **Последствия:** возможна меньшая доля успешных ответов у «защищённых» источников; нет юридического риска и нет расходов на прокси.

### ADR-VL-12
**Приоритеты очереди в доках — устарели** · принято

- **Контекст:** ПРОТ-05 — доки 13, 15, 23 описывали приоритеты/aging/refine-приоритет.
- **Решение:** эти формулировки помечены устаревшими; АНП-83 не применима.
- **Последствия:** канон — ADR-VL-05; при возврате к приоритетам нужен отдельный ADR.

### ADR-VL-13
**Фикс Jackson 2→3 и снятие `@ResponseStatus`** · принято

- **Контекст:** ПРОТ-23/24 — в `entity/atlas/*` аннотации Jackson 2 при Jackson 3 в проекте; 9 исключений с `@ResponseStatus(BAD_GATEWAY)`.
- **Решение:** перевести аннотации на Jackson 3 (`tools.jackson`); убрать `@ResponseStatus` — статус назначает `GlobalExceptionHandler` по `ErrorCode`.
- **Последствия:** сериализация перестаёт молча ломаться; наружу не протекёт `502` от внутренних исключений.

### ADR-VL-14
**Warmup и retry — в гейтвеях, без `BzdService`/`BelHotelService`** · принято

- **Контекст:** ПРОТ-25 — в плане предлагались отдельные сервисы с warmup внутри клиента.
- **Решение:** `BzdService`/`BelHotelService` не заводим; warmup и retry-cookie — внутри гейтвеев + `WarmupScheduler` (старт и повтор 5 мин; ошибка warmup → повтор через 30 с, падения нет).
- **Последствия:** меньше слоёв; warmup-логика тестируется вместе с гейтвеем.
