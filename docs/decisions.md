# Журнал архитектурных решений (ADR)

Канонический реестр решений проекта StormEvent. Каждое решение карточкой: **дата · контекст · решение · последствия · статус**.
Источники: [`25_contradictions.md`](25_contradictions.md) (27 противоречий ПРОТ-01…27 и ответы владельца), [`24_implementation_plan.md`](24_implementation_plan.md) (ФАЗА 0, шаги 5–40 + блок 40.1).

## Как читать номера

| Серия | Что это | Статус |
|---|---|---|
| `ADR-001…ADR-016` | Базовые технические решения ФАЗЫ 0 (БД, доступ, миграции, очередь, клиенты, LLM, TZ) | принято, часть — **заменено** `ADR-VL-15` |
| `ADR-VL-01…ADR-VL-16` | **Решения владельца** (канон; помечены в плане как `[ВЛ]`, спорить не нужно) | принято |
| `ADR-017…ADR-052` | Черновики «на ходу» внутри шагов плана (напр. `NamedParameterJdbcTemplate`, `jsonb`) | не канон — в реестр попадут при реализации |

Легенда статусов: **принято** · **действует** · **уточнено** (ссылка на уточняющее решение) · **заменено** (ссылка на замену) · **отменено** (ссылка на ПРОТ/ADR).

Правило: изменение любого принятого решения = новая карточка со статусом «заменено» у старой. Решения владельца меняются только новым решением владельца.

## Базовые решения

### ADR-001
**База данных — PostgreSQL 16** · принято · 2026-09-26

- **Контекст:** нужны реляционные данные (сессии, кэш, состояния источников, логи, агрегаты метрик), TTL-чистки, индексы, транзакции сессий.
- **Решение:** PostgreSQL 16, поднимается через Docker Compose (`compose.yml`, `localhost:5432`). Схема `storm`.
- **Последствия:** нужны `spring-boot-starter-jdbc`, драйвер `postgresql`, `flyway-core`. Миграции — единственный способ менять схему.
- **Обоснование** (требование → механизм PG 16):

  | Требование | Механизм |
  |---|---|
  | агрегаты метрик (`stats_source_hourly`, `source.errors{source,type}`) | `GROUP BY` + `count(*) filter (where ...)` по `source_error_log`; отчёт считает БД, а не приложение |
  | TTL-чистки сессий (15 мин, ADR-VL-02) и кэша | индекс по `expires_at` + `DELETE … WHERE expires_at < now() LIMIT 1000` в одной транзакции (шаг 235) |
  | кэш с протуханием | `expires_at`/`stale` — колонки, а не `SETEX`: можно отдать протухшее как fallback |
  | состояния источников (`source_state`) | natural key `source` как PK + `INSERT … ON CONFLICT DO UPDATE` (upsert) |
  | логи `request_log` / `source_error_log` | append-only + нативное партиционирование по `created_at` + retention 90 дней (шаги 230–234) |
  | транзакции сессии | реплики в `session_message` + `touch` `session.last_access_at` атомарно |
  | дедупликация по `requestId` | уникальный PK `idempotency` — гарантия на уровне БД, а не в коде (шаг 187) |

- **Почему не KV-хранилище:** у Redis нет вторичных индексов — отчёт по метрикам превращается в `SCAN` по ключам; TTL реализуется через `keyspace notification`/вытеснение вместо предсказуемого `expires_at`-индекса; транзакции ограничены; второе хранилище = вторая точка отказа (ПРОТ-18).
- **Альтернативы:**
  - **H2** — только тесты (ADR-004): нет `jsonb`, партиционирования и нативных `SKIP LOCKED`, прод- и тест-режимы расходятся.
  - **Redis** — не берём: годится на кэш/сессии, но не на метрики (см. «Почему не KV»); кэш и сессии живут в Postgres (ADR-005).
  - **MySQL 8** — функционально близок, но уступает по `jsonb`-фильтрам, партиционированию и `RETURNING`; выигрыша при единственной БД в MVP нет.
  - **ClickHouse/TimescaleDB** — подходят для тяжёлой аналитики логов, но это лишний сервис на этапе, где логи пишут 5 источников под нагрузкой MVP (ADR-006).

### ADR-002
**Доступ к БД — Spring Data JDBC + JdbcTemplate, без JPA** · принято

- **Контекст:** доменная модель (`Offer` и сущности источников) не является картой таблиц; JPA-магия мешает тонкому контролю SQL.
- **Решение:** `NamedParameterJdbcTemplate` (безопасно по SQL-инъекциям) + репозитории в пакете `repository`; в сервисах SQL не пишем.
- **Последствия:** больше ручного маппинга, предсказуемые планы запросов; unit-тесты на репозитории — с H2.
- **Уточнение термина:** под «Spring Data JDBC» понимается связка `spring-boot-starter-jdbc` + `NamedParameterJdbcTemplate`. Модуль `org.springframework.data:spring-data-jdbc` (репозитории-интерфейсы, `@Query`, маппинг `@Entity`) **не подключаем** — по духу он близок к JPA, именно его маппинг и не нужен. Черновики «ADR-020»/`ADR-021» (шаги 96, 102) фиксируют это на уровне кода.
- **Обоснование** (требование → почему хватает `JdbcTemplate`):

  | Требование | Механизм |
  |---|---|
  | доменная модель отделена от таблиц | `Offer`, `AtlasRide`, `BzdTrain` — DTO внешних источников, в БД не персистятся (офферы и комбо считаются на лету, шаг 202); персистятся только `session`, `session_message`, `cached_result`, `source_state`, логи. В JPA появился бы второй параллельный набор классов под ту же логику |
  | состояния источников | `INSERT … ON CONFLICT DO UPDATE` по natural key `source` (шаг 211) |
  | TTL-чистки пачками | `DELETE … WHERE expires_at < now() LIMIT 1000` в одной транзакции (шаг 235) |
  | агрегаты метрик | `count(*) filter (where code = :code)` за окно (шаги 220–222) |
  | лог-таблицы | batch insert через `NamedParameterJdbcTemplate.batchUpdate` + `rewriteBatchedStatements=true` (шаги 223, 226) |
  | дедупликация `requestId` | `INSERT … ON CONFLICT DO NOTHING` в `idempotency` — конфликт не превращается в исключение в коде (шаг 187) |
  | партиционирование логов | нативный SQL к партициям, без абстракции сущностей (шаги 230–234) |
  | отсутствие N+1 | нет lazy-loading: всё грузится явно, сессия не падает в закрытом `EntityManager` |

  Плюс: параметры `NamedParameterJdbcTemplate` биндятся, а не склеиваются в строку — SQL-инъекции исключены на уровне API, а не дисциплиной.
- **Альтернативы:**
  - **JPA / Hibernate** — `ddl-auto` против Flyway (ADR-003), lazy-loading с N+1, кэш второго уровня, `@Entity`-маппинг классов, которые в БД не живут. Нативные upsert/batch/партиционирование в JPA пишутся как `@Query(nativeQuery = true)`, то есть тот же SQL + лишняя обвязка.
  - **Spring Data JDBC** (репозитории-интерфейсы, `@Query`, `@Id`) — по духу близок к JPA, маппинг сущностей нам не нужен; берём только `spring-boot-starter-jdbc`.
  - **MyBatis** — SQL пишется руками так же, но XML-маппинг и ручной разбор `ResultSet` без выигрыша против `NamedParameterJdbcTemplate`.
  - **jOOQ** — type-safe SQL с кодогенерацией по схеме; окупается на десятках таблиц, а в MVP их восемь — лишняя генерация кода в сборке.
  - **Чистый `JdbcTemplate` без Spring** — теряем автотранзакции, `TransactionTemplate` и интеграцию с тестовым контекстом; экономия нулевая.

### ADR-003
**Миграции — Flyway** · принято

- **Контекст:** несколько разработчиков и окружений, нужен единый источник правок схемы.
- **Решение:** `flyway-core`, версии `V1…Vnn`; ручной `ALTER` запрещён (ADR-040).
- **Последствия:** схема в репозитории; в тестах Flyway либо отключается, либо работает на H2 в PostgreSQL-режиме.
- **Обоснование:** миграции — единственный воспроизводимый способ поднять схему (`compose.yml` → `mvn spring-boot:run` → `\dt`); ручной `ALTER` в проде расходится с репозиторием и ломает тесты. `V<n>__<описание>.sql`, каждый индекс — отдельная миграция (шаги 128–129). В H2 те же `V`-файлы применяются (шаг 114), поэтому DDL пишем на общем подмножестве PG и `MODE=PostgreSQL`.
- **Альтернативы:** `Liquibase` — XML/YAML-описание изменений вместо SQL, слабее для нативных конструкций PG; `ddl-auto` Hibernate — генерирует схему из кода, с прод-схемой не сверяется (и несовместимо с «без JPA»); ручной SQL-скрипт без версионирования — нет истории, нет отката.

### ADR-004
**Тестовая БД — H2 в PostgreSQL-режиме** · принято

- **Контекст:** тесты должны идти без Docker.
- **Решение:** H2 (`MODE=PostgreSQL`) для юнит/интеграционных; `Testcontainers` — опционально для pg-специфики (партиционирование, jsonb).
- **Последствия:** если jsonb мешает — маппинг через `JsonNode` из `TEXT` (черновик «ADR-028» в плане).
- **Обоснование:** Docker в каждом прогоне `mvn test` — минуты на старт и зависимость от окружения; H2 в PostgreSQL-режиме даёт тесты за секунды и покрывает CRUD, индексы, транзакции, TTL-выборку (шаги 210–222). Где нужна настоящая семантика PG (`jsonb`-фильтры, партиционирование `V11`/`V12`, `SKIP LOCKED`) — включается `Testcontainers`-профиль, а не усложнение основного набора (ADR-VL-06: без Prometheus, свои счётчики).
- **Альтернативы:** реальный Postgres через Testcontainers на каждый тест — медленно, но честно; держать «тесты на прод-БД» — не воспроизводимо; in-memory реализации (H2 без `MODE=PostgreSQL`) — расхождение диалектов ловится только на проде.

### ADR-005
**Кэш и сессии поверх Postgres, без Redis** · принято

- **Контекст:** ПРОТ-18 — лишняя инфраструктура ради MVP.
- **Решение:** таблицы `cached_result`, `session`, `session_message`; in-memory кэш как ускоритель, но не источник истины.
- **Последствия:** сессии переживают рестарт; кэш общий для всех инстансов; нужны housekeeper-задачи.
- **Обоснование:** то, что мы храним, уже реляционное и требует SQL-доступа, поэтому отдельное KV-хранилище дублировало бы одну и ту же БД (ADR-001). Сессия = диалог (`session_message`, TTL 15 мин с последнего обращения, ADR-VL-02) — это история реплик с FK и каскадным удалением, а не значение по ключу. Кэш источников (`cached_result`) хранит `source`/`domain`/`expires_at`/`stale` и чистится по индексу — в Redis это ключи без вторичных индексов, плюс невозможен «протухшее, но отдаём как fallback».
- **Альтернативы:** **Redis** — быстрее по чтению, но второе хранилище в MVP не окупается (ПРОТ-18) и не умеет агрегировать метрики; **in-memory `ConcurrentHashMap` без БД** — кэш теряется при рестарте и разъезжается между инстансами (источник истины только в одном процессе); **выбор: оставить in-memory кэш как ускоритель** — допустимо, но не как единственное хранилище.

### ADR-006
~~**Очередь запросов — `ArrayBlockingQueue(100)`, FIFO**~~ · **ЗАМЕНЕНО** ([ADR-VL-15](#adr-vl-15)) · 2026-09-26

- **Контекст:** ПРОТ-05, У-6 — в доках были `PriorityBlockingQueue` + aging + ramp-up.
- **Решение:** один in-memory FIFO-очередь на 100 задач, 4–8 воркеров, дедупликация по `requestId`; аудит в `request_log`.
- **Последствия:** порядок обработки = порядок поступления; переполнение → 503 + `Retry-After: 5` (ADR-VL-05). Распределённой очереди нет — архитектура single-node (черновик «ADR-045»).
- **Почему заменено:** решение владельца [ADR-VL-15](#adr-vl-15) — очередь, воркеры и backpressure в MVP не делаем, всё синхронно. `request_log` (аудит) сохраняется, дедупликация `requestId` переезжает в таблицу `idempotency` (ADR-001).

### ADR-007
**Схема пакетов — по блюпринту 23, circuit исключить** · принято

- **Контекст:** ПРОТ-08/09 — circuit breaker вычеркнут из MVP.
- **Решение:** `gateway/normalize/orchestration/agent/cache/session/queue/scheduler/exception/web/handler/metrics`; пакета `circuit` нет.
- **Последствия:** быстрый сбой источника — только по `source_state.enabled`/`draining`; спека breaker'а остаётся в `16` и `23` как материал для будущей задачи.
- **Уточнено** [ADR-VL-15](#adr-vl-15): из списка пакетов убран `queue` (`RequestQueue`, `RequestTask`, `QueueProperties`, `BackpressurePolicy`) — очереди в MVP нет.

### ADR-008
~~**HTTP-клиенты — базовый + производные `newBuilder()`**~~ · **ЗАМЕНЕНО** ([ADR-VL-15](#adr-vl-15))

- **Контекст:** ПРОТ-03 — в блюпринте был «единственный клиент, пул 5», из-за чего тяжёлые POST (BZD, TicketBus) блокировали лёгкие.
- **Решение:** несколько `OkHttpClient` разрешены: базовый + производные с per-source таймаутами/пулами, отдельный профиль для SSE.
- **Последствия:** `OkHttpProperties` расширяется overrides'ами вида `source-*.timeout-ms`; таймауты задаются явно (никаких «бесконечных» `callTimeout=0`).
- **Почему заменено:** клиенты разделяли только ради параллелизма ([ADR-VL-15](#adr-vl-15) — вызовы последовательные). В MVP **один** `OkHttpClient` с одним набором таймаутов; SSE-клиент и per-source `ConnectionPool` не заводим.

### ADR-009
~~**Fan-out к источникам — виртуальные потоки Java 21**~~ · **ЗАМЕНЕНО** ([ADR-VL-15](#adr-vl-15))

- **Контекст:** параллельный опрос 5 источников на каждый запрос.
- **Решение:** `Thread.ofVirtual().name("src-<source>")`, без пула на источник; MDC пробрасывается в дочерние потоки.
- **Последствия:** дёшево создавать задачу на источник; ограничитель — таймауты и semaphores на тяжёлых источниках.
- **Почему заменено:** в Java 21 виртуальные потоки — preview (`--enable-preview`), выигрыш нужен на тысячах одновременных блокирующих вызовов, которых в MVP нет; последовательный вызов 5 источников проще и предсказуемее ([ADR-VL-15](#adr-vl-15)). Класс переименован в `SourceExecutor`: обходит источники по порядку, без потоков и `CompletableFuture`; сбор результатов — отдельный `ResultCollector`.

### ADR-010
**Общий deadline 15 с с отменой незавершённых задач** · **ОТМЕНЕНО**

- **Контекст:** в плане была deadline-модель с бюджетом 90 % и `future.cancel(true)`.
- **Решение владельца:** общего дедлайна нет — **ждём все источники**; `deadlineMs` — advisory; отмены нет (ПРОТ-01/02, У-6, У-7). **[ВЛ]** «Ждём все» = последовательно, ограничение даёт общий таймаут клиента ([ADR-VL-15](#adr-vl-15)).
- **Последствия:** см. [ADR-VL-03](#adr-vl-03) и [ADR-VL-09](#adr-vl-09); тесты «TIMEOUT к deadline» и `ParallelFactorCancelTest` сняты.
- **Уточнено** [ADR-VL-16](#adr-vl-16): бюджет времени **вернулся**, но в другой форме — 40 с мягко / 60 с потолок с `REQUEST_TIMEOUT`/504. Прежняя модель (90 % на источники, `future.cancel(true)`, обрыв всего сразу) по-прежнему не действует, поэтому карточка остаётся отменённой.

### ADR-011
**`requestId` генерируется на входе** · принято

- **Контекст:** нужна сквозная трассировка HTTP → инструмент → источник → парсер → ответ.
- **Решение:** `RequestIdFilter` кладёт `requestId` в MDC и в `request_log`/`source_error_log`; заголовок запроса используется, если присутствует.
- **Последствия:** пользовательские сообщения об ошибках не содержат JSON-конверта, но `requestId` всегда в логах (ADR-VL-01).

### ADR-012
**LLM за интерфейсом `LlmGateway`, провайдер — OpenRouter** · принято

- **Контекст:** У-4, В-9 — нужен реальный LLM с function calling; ключ появится позже.
- **Решение:** интерфейс `LlmGateway` (agentic-режим: `nextTools(...)` + `complete(...)`); конфиг из `OPENROUTER_API_KEY` / `OPENROUTER_MODEL`; при отсутствии ключа — fallback без LLM.
- **Последствия:** смена провайдера не трогает агент; тесты LLM — на моках; `RuleBasedFallback` живёт параллельно.

### ADR-013
**Порядок фаз реализации** · принято, уточнено [ADR-VL-15](#adr-vl-15)

- **Решение:** БД → исключения → модель → гейтвеи → параллельность → инструменты → combiner → LLM → web → очередь/сессии/кэш → метрики → E2E. Circuit breaker не делаем.
- **Последствия:** каждая фаза заканчивается зелёными тестами и карточкой в этом реестре.
- **Уточнение:** фазы «параллельность» и «очередь» из порядка убраны (ADR-VL-15): БД → исключения → модель → гейтвеи → инструменты → combiner → LLM → web → сессии/кэш → метрики → E2E.

### ADR-014
**Именование таблиц snake_case; PK — `bigint identity` или UUID** · принято

- **Решение:** ссылки между таблицами — UUID (`session_id`, `request_id`); суррогатные логи — `bigint identity`.
- **Последствия:** естественные ключи для состояний источников — имя источника (черновик «ADR-031»).

### ADR-015
**Идентификаторы сущностей источников — `source:kind:externalId`** · принято

- **Решение:** строковые id вида `atlasbus:ride:12345`, в БД `varchar(128)` с уникальным индексом.
- **Последствия:** дедупликация между источниками возможна; id переживает смену БД.

### ADR-016
**Временные зоны — Europe/Minsk** · принято · ПРОТ-15

- **Контекст:** расчёты, стыковки, границы суток и отображение для пользователя из РБ.
- **Решение:** все расчёты и отображение в `Europe/Minsk`; в БД `timestamptz` (технически UTC), API отдаёт `+03:00`.
- **Последствия:** агрегаты метрик считаются по UTC-часам (черновик «ADR-035»), пользовательские границы суток — по Минску.

## Решения владельца (канон)

> Помечены в плане как `[ВЛ]`, в доках — как `[ВЛ]`/`[ОТМЕНЕНО]`. Основание: ответы владельца по противоречиям ПРОТ-01…27 и вопросам У-1…У-8 / В-1…В-15 (`25_contradictions.md`, разделы 0, 0.1, 0.2).

### ADR-VL-01
**Текстовый контракт: один чат-эндпоинт, ответ `text/plain`** · принято

- **Контекст:** ПРОТ-13/16/17 — в доках был JSON `SearchResponse`/`ResponseDto`/`openapi.yml` и три эндпоинта (`search`, `refine`, `sessions/{id}`); У-1, В-7.
- **Решение:** `POST /api/v1/agent/chat`, вход `{sessionId?, text}`, ответ — **строка** `text/plain`. Отдельных `search`/`refine` и структурированного JSON нет. SSE наружу не отдаём.
- **Последствия:** проще клиент и фронт; теряем машинную интеграцию (когда понадобится — отдельное решение). Ошибки источников передаются в тексте, а не кодом ответа.

### ADR-VL-02
**Сессия-чат в Postgres, TTL 15 минут** · принято

- **Контекст:** ПРОТ-06/07 — расходились TTL 30/60 мин и 15 мин idle, `session_refine` против истории диалога; У-2.
- **Решение:** сессия = диалог; таблица `session_message` (роль/текст/время/`requestId`); TTL **15 мин** с последнего обращения; состояния `NEW|ACTIVE|EXPIRED` (без `CANCELLED`).
- **Последствия:** `session_refine` не делаем; контекст для LLM = последние 20 сообщений; истёкшая сессия → `SESSION_EXPIRED` и новый `sessionId`.

### ADR-VL-03
**Агентный цикл: LLM выбирает инструменты, мы ждём все источники** · принято

- **Контекст:** ПРОТ-14/22; В-11/В-12/В-13; раздел 0.2.
- **Решение:** OpenRouter function calling: LLM возвращает `tool_calls` → инструменты-источники выполняются **параллельно** → fan-in **ждёт все** → результаты (`{status, offers|error}`) возвращаются в LLM → повтор до `maxToolRounds` → финальный текст. Контекст — вся сессия, максимум 20 сообщений. Лимит раундов — на уровне агента (`AgentProperties.llm.maxToolRounds`, по умолчанию 2 + правило в системном промпте; жёсткой остановки в коде нет).
- **Последствия:** фиксированного маппинга «интент → инструмент» нет, `forceSource` отменён; до появления ключа работает fallback-решатель с тем же интерфейсом; позже так же настроим для n8n.
- **Уточнено** [ADR-VL-15](#adr-vl-15): инструменты-источники вызываются **последовательно**, а не параллельно; «ждём все» означает «дождались каждого вызова, упавший не отменяет остальные». Всё остальное решение (LLM выбирает инструменты, контекст 20 сообщений, лимит раундов) в силе.

### ADR-VL-04
**Circuit breaker отложен** · принято

- **Контекст:** ПРОТ-08…12, В-8 — в доках был breaker (5 ошибок/30 с → OPEN на 60 с, HALF_OPEN, `circuit_state`, `pausedUntil`, метрика `source.circuit`).
- **Решение:** в MVP **не делаем**: ни состояний CLOSED/OPEN/HALF_OPEN, ни таблицы `circuit_state`, ни проб, ни пауз. Вместо: таймауты клиента ([ADR-VL-15](#adr-vl-15)), алерт по счётчику ошибок, ручной флаг `source_state.enabled` (+`draining`) с `X-Api-Key`.
- **Последствия:** источник не «отключается» сам — падает, упоминается в тексте, деградация видна в метриках и алертах; оператор решает вручную. Спека breaker'а сохранена в `16_unhappy_circuit_switch.md` и `23_impl_blueprint.md` как материал для будущей задачи.

### ADR-VL-05
~~**Очередь простая: FIFO, без приоритетов и aging**~~ · **ЗАМЕНЕНО** ([ADR-VL-15](#adr-vl-15))

- **Контекст:** ПРОТ-05, ПРОТ-12, У-6 — в доках были `PriorityBlockingQueue`, aging, `pausedUntil`/cooldown, приоритет refine-запросов.
- **Решение:** `ArrayBlockingQueue(100)`, FIFO, 4–8 воркеров, дедупликация по `requestId`; переполнение → **503** `QUEUE_REJECTED` + `Retry-After: 5`.
- **Последствия:** нет «счастливых» пользователей при перегрузке — честный FIFO; поля `priority` в контракте нет.
- **Почему заменено:** владелец решил убрать очередь целиком, а не упрощать её ([ADR-VL-15](#adr-vl-15)).

### ADR-VL-06
**Наблюдаемость: без Prometheus/actuator, свои счётчики + алерты** · принято

- **Контекст:** ПРОТ-20/21 — в плане был `/actuator/prometheus` и Grafana.
- **Решение:** Prometheus и actuator не подключаем; счётчики в памяти (`MetricsCollector`) + `AlertEvaluator` с логом WARN/ERROR (пороги в конфиге), имена метрик — по единому словарю.
- **Последствия:** выгрузка метрик во внешнюю систему — отдельное решение позже; сейчас хватает логов и алертов.

### ADR-VL-07
**Ошибки источников: 403 без retry, один запрос = одна ошибка** · принято

- **Контекст:** ПРОТ-04/10/11 — в доках 403 открывал circuit и запускал бесконечный retry; ошибки источника терялись в partial.
- **Решение:** `403` → сообщение пользователю **без повторов**; `401` → **один** warmup-retry; `429`/`503` → ошибка сразу, **без retry и без пауз**; `retry` одного логического запроса = **одна** ошибка в метриках; упавший источник **всегда** упоминается в тексте ответа.
- **Последствия:** метрика ошибок не раздувается ретраями; пользователь всегда видит, какие источники не ответили.

### ADR-VL-08
**Модель оффера: цены и тарифы подробно, остальное минимум** · принято

- **Контекст:** ПРОТ-19, В-10 — в модели были избыточные поля, в другом доке — минимум без тарифов.
- **Решение:** подробно — цены и тарифы (`price` + `currency`, `tariffName`/`class`, `seats`); минимум — `from`, `to`, дата/время, `source`, `kind`, `url`/`externalId`. `attributes`, `baggage`, `documents`, `cancellation`, `transfers` — после MVP.
- **Последствия:** `Offer` компактный и достаточный для MVP; детальные тарифы отдельными полями, а не в `attributes`.

### ADR-VL-09
**Отмена запроса пользователем не делается** · принято

- **Контекст:** У-7 — в плане были `CANCELLED`, `AbortController`, отмена задач и SSE-потоков.
- **Решение:** пользователь не может отменить запрос; состояния `CANCELLED` нет.
- **Последствия:** обход источников всегда доводит каждый начатый вызов до конца (ограничен таймаутом вызова, [ADR-VL-15](#adr-vl-15), [ADR-VL-16](#adr-vl-16)); тесты отмены сняты; «убийство» потоков по флагу отключения источника не делаем (только `draining`).
- **Уточнено** [ADR-VL-16](#adr-vl-16): длительность вызовов теперь ограничена бюджетом времени запроса (40 с мягко, 60 с — потолок с 504). Это **не отмена**: уже начатый вызов не прерывается, а новый не начинается, если в бюджет не влезает. `cancel()`/`AbortController` по-прежнему не используются.

### ADR-VL-10
**Админка и диагностика — за `X-Api-Key`** · принято

- **Контекст:** ПРОТ-26 — эндпоинты управления источниками были без защиты.
- **Решение:** `/api/v1/sources/**` и `/api/v1/diagnostics/**` требуют заголовок `X-Api-Key` со значением из `STORM_ADMIN_KEY` + CORS-whitelist.
- **Последствия:** секьюрти конфигом, без ролей; в тестах — заглушка фильтра; секрет только в env.

### ADR-VL-11
**Обход anti-bot не делаем** · принято

- **Контекст:** ПРОТ-27 — в доках были headless, «реалистичный fingerprint», residential proxy.
- **Решение:** уважаем `robots.txt`; при капче/Cloudflare — сообщение пользователю + алерт, источник отключается вручную.
- **Последствия:** возможна меньшая доля успешных ответов у «защищённых» источников; нет юридического риска и нет расходов на прокси.

### ADR-VL-12
~~**Приоритеты очереди в доках — устарели**~~ · **ОТМЕНЕНО** ([ADR-VL-15](#adr-vl-15))

- **Контекст:** ПРОТ-05 — доки 13, 15, 23 описывали приоритеты/aging/refine-приоритет.
- **Решение:** эти формулировки помечены устаревшими; АНП-83 не применима.
- **Последствия:** канон — ADR-VL-05; при возврате к приоритетам нужен отдельный ADR.
- **Почему отменено:** очередь в MVP нет вообще ([ADR-VL-15](#adr-vl-15)) — помечать устаревшим нечего; разделы про очередь в доках 13, 15, 23, 25 помечены как отменённые целиком.

### ADR-VL-13
**Фикс Jackson 2→3 и снятие `@ResponseStatus`** · принято

- **Контекст:** ПРОТ-23/24 — в `entity/atlas/*` аннотации Jackson 2 при Jackson 3 в проекте; 9 исключений с `@ResponseStatus(BAD_GATEWAY)`.
- **Решение:** перевести аннотации на Jackson 3 (`tools.jackson`); убрать `@ResponseStatus` — статус назначает `GlobalExceptionHandler` по `ErrorCode`.
- **Последствия:** сериализация перестаёт молча ломаться; наружу не протекёт `502` от внутренних исключений.

### ADR-VL-14
**Warmup и retry — в гейтвеях, без `BzdService`/`BelHotelService`** · принято

- **Контекст:** ПРОТ-25 — в плане предлагались отдельные сервисы с warmup внутри клиента.
- **Решение:** `BzdService`/`BelHotelService` не заводим; warmup и retry-cookie — внутри гейтвеев + `WarmupScheduler` (старт и повтор 5 мин; ошибка warmup → повтор через 30 с, падения нет).
- **Последствия:** меньше слоёв; warmup-логика тестируется вместе с гейтвеем.

### ADR-VL-15
**Синхронное выполнение: один `OkHttpClient`, без очереди, воркеров и виртуальных потоков** · принято · 2026-09-27

- **Контекст:** ПРОТ-01, ПРОТ-03, ПРОТ-05, У-6; заменяет [ADR-006](#adr-006), [ADR-008](#adr-008), [ADR-009](#adr-009), [ADR-VL-05](#adr-vl-05). В плане и доках было: `ArrayBlockingQueue(100)` + 4–8 воркеров + backpressure (`QUEUE_REJECTED`, `Retry-After`), `PriorityBlockingQueue`/aging, параллельный fan-out на виртуальных потоках Java 21, производные `OkHttpClient` (SSE-пул, per-source таймауты) и семафоры под Atlas. Нагрузка MVP (единицы одновременных пользователей) этого не требует, а сложность мешает: пять источников, текстовый контракт, без SSE и без отмены.
- **Решение:** в MVP всё выполняется **синхронно, в потоке HTTP-запроса**:
  1. **один** `OkHttpClient` — один бин, один набор таймаутов (`connect`/`read`/`call` задаются явно, никаких per-source override'ов и отдельного SSE-пула);
  2. инструменты-источники вызываются **последовательно**, в том порядке, который вернул LLM; ни виртуальных потоков, ни `ExecutorService`, ни `CompletableFuture`-fan-out;
  3. `RequestQueue`/`RequestTask`/воркеры/backpressure/лимит 100 — **не делаем**; пакета `queue/` нет, метрик `queue.*` нет;
  4. `QUEUE_REJECTED` (503) и `Retry-After` не выдаём; код остаётся в `ErrorCode` как неиспользуемый, 429 остаётся только для rate-limit по пользователю;
  5. `request_log` (аудит каждого запроса) остаётся, дедупликация по `requestId` — таблица `idempotency` (ADR-001), а не очередь;
  6. ограничение нагрузки — таймауты общего клиента (connect/read/call) и лимит раундов агента `maxToolRounds`; backpressure делает сам Tomcat числом потоков запросов; **потолок времени ответа задаёт бюджет запроса** ([ADR-VL-16](#adr-vl-16)) — вопрос per-source таймаутов закрыт.
- **Обоснование** (требование → механизм):

  | Требование | Механизм |
  |---|---|
  | не упереться в лимит очереди | очередь не нужна, пока один пользователь = один поток Tomcat; N пользователей = N запросов к источникам подряд |
  | не копить задачи в памяти | задач в памяти нет вообще (АНП-86/АНП-88 снимаются) |
  | предсказуемое время ответа | фиксированный порядок вызовов + явные таймауты клиента; нет «дождался всех случайно» |
  | аудит | `request_log` (шаги 190–191, 230–234) + `requestId` в MDC (ADR-011) — очередь для аудита не нужна |
  | защита от двойного клика | `idempotency`: `INSERT … ON CONFLICT DO NOTHING` (шаг 187) |
  | нагрузка на источник (Atlas не любит частоту, HP-72) | последовательные вызовы + таймаут клиента; `Semaphore(1)` на warmup BZD остаётся (АНП-80) |
  | дебаг и разработка | нет пулов, семафоров, `queue.reject` и preview-фича `--enable-preview` в Java 21 |

- **Последствия:**
  - **Минус — скорость:** без отдельного бюджета худший случай был бы суммой таймаутов пяти источников подряд (при `read` 10 с это до ~50 с + LLM). Поэтому введены жёсткие границы: **40 с мягкий бюджет и 60 с потолок с 504** ([ADR-VL-16](#adr-vl-16)); внутри бюджета остаются короткие общие таймауты, обязательный кэш (TTL 5 мин) и вызов дешёвых источников первыми.
  - **Плюс — меньше кода:** из ФАЗЫ 14 уходят шаги 803–816, 840, 845, 846, 849; снимаются тесты `QueueRejectTest`, `E2eQueueTest`, `ParallelExecutorFanOutTest` (на виртуальные потоки); `ParallelExecutor` переименован в `SourceExecutor` (последовательный обход), сбор результатов — `ResultCollector`.
  - Порядок результатов — **порядок вызова**, а не «по завершению»; «ждём все источники» (ADR-VL-03) сохраняется в смысле «упавший источник не отменяет остальные и попадает в `warnings`» (ADR-VL-07).
  - `/api/v1/health/ready` больше не проверяет очередь: только БД и «все источники выключены» (шаг 55).
  - Порядок фаз (ADR-013) теряет «параллельность» и «очередь».
  - Агентный цикл, сессии, кэш, метрики, алерты, E2E — без изменений.
  - Это **не** упрощение на будущее: если понадобится нагрузка, несколько инстансов или честный backpressure, вернуться придётся отдельным решением владельца (ADR-006/008/009 остаются в реестре как заменённые).
- **Альтернативы:**
  - **Виртуальные потоки (ADR-009)** — в Java 21 это preview (`--enable-preview` в `pom.xml` нет), выигрыш появляется на тысячах одновременных блокирующих вызовов, а не на десятках; сверху пиннинг под `synchronized` и нечитаемые thread dump'ы. На MVP — риск без выгоды.
  - **Вернуть очередь `ArrayBlockingQueue(100)` (ADR-006/ADR-VL-05)** — даёт backpressure и дедуп, но требует воркеров, политики reject, метрик и `queue.reject` в health, при этом не снимает ограничения single-node.
  - **Производные `OkHttpClient` под SSE и тяжёлые источники (ADR-008)** — существовали ради параллелизма; при последовательных вызовах это лишние пулы, а SSE-стриминг в MVP и так отменён (ADR-VL-01).
  - **Фиксированный `ExecutorService` + семафоры** — промежуточный вариант (ограниченный параллелизм без preview-флагов); сознательно не выбран, чтобы не подбирать размер пула вслепую. Вернуться к нему проще всего, если синхронный вариант не потянет.
  - **Внешняя очередь (Kafka / RabbitMQ / Redis Streams / очередь-таблица в PG)** — лишняя инфраструктура и второй источник правды поверх ADR-001/ADR-005.

### ADR-VL-16
**Бюджет времени запроса: 40 с мягко, 60 с — жёсткий потолок с 504** · принято · 2026-09-27

- **Контекст:** ADR-VL-15 оставил единственное ограничение — таймауты общего клиента, а в коде `OkHttpProperties.callTimeoutMs = 0`, то есть **бесконечно** (шаг 29 плана, `OkHttpProperties.java`). При последовательных вызовах худший случай = сумма таймаутов пяти источников подряд + 30 с LLM (ADR-VL-15, «Минус — скорость»). Владельцу нужен предсказуемый потолок ответа: **суммарно не больше 40 секунд**, «запросы как успеют, оставшееся время — на нейронку». Плюс страховка: **максимум 1 минута**, не успели — ошибка клиенту. Это частично возвращает идею общего дедлайна (ADR-010), но **без отмены** (ADR-VL-09).
- **Решение:**
  1. **Мягкий бюджет 40 с** — его делят источники и LLM. В `RequestContext` появляется `budgetDeadlineAt = start + 40 с` (монотонное время).
  2. **Перед каждым вызовом источника** `SourceExecutor` считает `remaining = budgetDeadlineAt − now`. Если `remaining ≤ minSourceCallMs` (по умолчанию 1 с) — вызов **не делается**, результат `SKIPPED_NO_BUDGET`, метрика `source.skipped`, предупреждение пользователю (ADR-VL-07). Иначе таймаут конкретного вызова = `remaining`.
  3. **Таймаут задаётся на вызов**, а не на клиент: `client.newCall(request).timeout().timeout(remaining, MILLISECONDS)`. В OkHttp 5 `Call.timeout()` — пер-вызововый `okio.Timeout`, общий путь `enter()/exit()` одинаков для синхронного `execute()`. Поэтому **второй `OkHttpClient` не нужен** — ADR-008 остаётся заменённым, per-source конфигов нет.
  4. **LLM получает остаток**: `min(remaining40, remaining60, llmTimeoutMs=30 c)`.
  5. **Жёсткий потолок 60 с.** Если к `start + 60 с` запрос не завершён — `REQUEST_TIMEOUT` → **HTTP 504**, даже если офферы уже собраны (решение владельца: «выдать ошибку клиенту», без частичного ответа). Никакого «покажем то, что нашли».
  6. **Отмены нет нигде.** Потолок гарантирован конструкцией: мы никогда не начинаем вызов, который не влезет в бюджет. `cancel()`/`future.cancel`/`AbortController` не появляются (ADR-VL-09).
  7. Новый код `REQUEST_TIMEOUT` в `ErrorCode` → 504. `QUEUE_REJECTED` (503) по-прежнему не выдаётся (ADR-VL-15).
  8. Конфиг: `storm.timeout.softBudgetMs=40000`, `storm.timeout.hardCeilingMs=60000`, `storm.timeout.minSourceCallMs=1000`; клиентский `okhttp.call-timeout-ms` = 60 000 (страховка для вызовов вне бюджета), read остаётся 10 с.
- **Обоснование** (требование → механизм):

  | Требование | Механизм |
  |---|---|
  | «суммарно не больше 40 с» | `budgetDeadlineAt` + проверка остатка **до** старта вызова; `callTimeout(remaining)` на каждом вызове |
  | «запросы как успеют» | источники не ждут друг друга; каждый получает ровно столько, сколько осталось в бюджете |
  | «оставшееся время — на нейронку» | LLM запускается после источников с `min(remaining40, remaining60, 30 c)` |
  | «максимум 1 минута, иначе ошибка» | `hardCeilingMs=60000` → `REQUEST_TIMEOUT`/504; проверяется и для источников, и для LLM |
  | один `OkHttpClient` | `Call.timeout()` меняет таймаут конкретного вызова, клиент и пул соединений не трогаем (ADR-008 заменён) |
  | без отмены | ничего не прерываем — просто не начинаем то, что не влезет (ADR-VL-09) |
  | честные метрики | `source.skipped` (нет бюджета) отдельно от `source.error` (таймаут) — видно, что виноват бюджет, а не источник |

- **Последствия:**
  - **Худший случай больше не «сумма пяти таймаутов», а 60 с** — предсказуемо для клиента и для алерта.
  - Убран бесконечный `callTimeoutMs = 0` из кода: это был реальный баг (зависший источник держал Tomcat-поток вечно).
  - «Ждём все источники» ([ADR-VL-03](#adr-vl-03)) теперь означает «в пределах бюджета»: источник, которому не досталось времени, **пропускается**, а не обрывается на середине.
  - `deadlineMs` из тела запроса остаётся **advisory** и не может поднять бюджет выше 40 с: клиент не управляет таймингом сервиса.
  - **Клиент обязан обрабатывать 504.** Это новая ветка в контракте: `ErrorCode.REQUEST_TIMEOUT`, ключ i18n, тест в матрице кодов (шаг 46).
  - Если источники заняли все 40 с — LLM не вызывается вовсе, и ответ 504. Владелец выбрал строгий вариант осознанно, поэтому **кэш (TTL 5 мин) и порядок «дешёвые источники первыми» становятся обязательными**, а не просто желательными.
  - Уточняет [ADR-VL-09](#adr-vl-09) (отмены по-прежнему нет, но длительность вызовов ограничена бюджетом) и [ADR-VL-15](#adr-vl-15) п. 6 — вопрос per-source таймаутов закрыт: таймаут считается от остатка бюджета, индивидуальных значений у источников нет.
  - ADR-010 остаётся **отменённым**: возвращается бюджет времени, но не его прежняя модель (90 % на источники, `future.cancel(true)`, обрыв всего сразу).
- **Альтернативы:**
  - **Отмена на 40 с** (`future.cancel(true)`, обрыв всего) — потребовала бы `CompletableFuture`/дочерних потоков, то есть возврата ADR-009/ADR-015; и прямо запрещена ADR-VL-09.
  - **Per-source таймауты (bzd 60 с, ticketbus 45 с)** — отвергнуто: 60 с не помещается в бюджет 40 с, а индивидуальные значения означают производные клиенты и пулы (ADR-008, уже заменён).
  - **Просто `okhttp.call-timeout-ms = 40000`** — ограничивает один вызов, но не сумму последовательных; при пяти источниках потолок по-прежнему ~200 с. Не решает задачу.
  - **Параллельный fan-out** — единственный способ сделать потолок равным максимуму, а не сумме, но отклонён владельцем (ADR-VL-09, ADR-VL-15).
  - **Ответ без LLM по шаблону, когда бюджет кончился** — предлагалось и отклонено владельцем: вместо дешёвого ответа клиент получает явную 504 и может повторить запрос.
  - **`SERVER` тоннели и увеличение Tomcat-таймаутов** — маскируют проблему на уровне инфраструктуры, а не приложения; не выбрано.
