# Горячие запросы: планы, решения, цифры

Документ отвечает на вопрос «почему такой индекс и такой план». Все цифры —
реальные `EXPLAIN ANALYZE` на PostgreSQL 16.15 (`postgres:16.15-alpine`) на
наборе, который повторяет работу приложения: 5 000 сессий, 50 000 строк
`request_log`, 40 000 строк `source_error_log`.

Планы снимаются одинаково: `ANALYZE` таблицы, затем `EXPLAIN (ANALYZE, BUFFERS)`
на том же запросе, что шлёт репозиторий.

## 1. `source_error_log`: выборка по источнику

Запрос диагностики «что ломалось у конкретного источника» (`SourceErrorLogRepository.findBySource`):

```sql
SELECT * FROM storm.source_error_log WHERE source = 'bzd' ORDER BY created_at DESC LIMIT 100;
```

| Вариант | Время | Строки просмотрено | План |
|---|---|---|---|
| Без составного индекса (V1–V3) | 0.70 мс | 543 | Index Scan по `source`, затем сортировка |
| V4: `(source, created_at DESC)` | **0.16 мс** | 100 | Index Scan, сортировка не нужна |

Индекс даёт 4.4× по времени и снимает сортировку: `ORDER BY created_at DESC
LIMIT 100` обслуживается самим индексом, в heap попадают ровно 100 строк вместо
всех строк источника. Это главный выигрыш фазы — диагностика источников
становится дешёвой на любом объёме журнала.

## 2. `request_log`: история одной сессии

```sql
SELECT * FROM storm.request_log WHERE session_id = ? ORDER BY created_at DESC;
```

Гипотеза была добавить `(session_id, created_at DESC)`. Замеры её не подтвердили:

| Объём | Только `session_id` (V1–V3) | С добавленным `(session_id, created_at DESC)` |
|---|---|---|
| 50 строк одной сессии | 0.10 мс | 0.15 мс |
| 20 000 строк одной сессии | 9.9 мс | 10.7 мс |

**Индекс не добавлен.** На селективной выборке выигрыша нет, на тяжёлой — хуже:
индекс добавляет запись в журнал при каждом INSERT и не помогает там, где
запрос возвращает все строки сессии. Лишний индекс на пишущей таблице — это
плата без выгоды, поэтому в V4 его нет.

## 3. Журналы без индексов по дате: что реально мешает

Оба журнала партиционированы по месяцу (ADR-033), но месячные партиции создаёт
`PartitionMaintenance.ensureUpcoming`, а DEFAULT-партиция всегда есть. Пока
партиция месяца не создана (или в базе лежат старые строки), запрос по дате
упирается в DEFAULT-партицию. Отсюда правило эксплуатации: партиция создаётся
заранее (`storm.db.partition-months-ahead=2`), а не «когда выросло».

## 4. Кэш: `getFresh`

```sql
SELECT * FROM storm.cached_result WHERE cache_key = ? AND expires_at > ?;
```

Работает по первичному ключу `cache_key` (V1). Проверка свежести — в условии
на стороне БД, приложение не читает строку, чтобы её отбросить: протухшая запись
не попадает в сеть и не занимает heap. Составной индекс по `(cache_key, expires_at)`
не создаётся — при уникальном ключе это та же выборка плюс лишний индекс на
пишущей таблице.

## 5. Метрики: `countSince` и `selectTopErrors`

```sql
SELECT count(*) FROM storm.source_error_log WHERE source = ? AND code = ? AND created_at >= ?;
```

Обслуживается индексом `idx_source_error_log_source_created` по
`(source, created_at DESC)`: источник отсекается по индексу, `code` проверяется
в heap уже по отобранным строкам, `count(*)` из индекса не требует heap вообще
(index-only scan при холодном кэше требует visibility map, но идёт по индексу).

`selectTopErrors` группирует по часу и источнику за окно — это срез
`stats_source_hourly`, а не журнала, поэтому индексы на нём не расширялись.

## Что специально не оптимизировано

| Идея | Почему нет |
|---|---|
| GIN-индекс по `jsonb` | Поиска по jsonb нет: кэш читается по `cache_key`, агрегаты считаются в Java (ADR-042) |
| `request_log (session_id, created_at)` | Замеры выше: выигрыша нет, плата — запись в индекс |
| Б materialized view под `selectTopErrors` | Данных мало, `stats_source_hourly` уже агрегат; решение при росте |
| Кэш HTML в `cached_result` | Кэш нормализован, размер строки ограничен (ADR-042) |
| Отдельный read-replica | Архитектура single-node (ADR-045) |
