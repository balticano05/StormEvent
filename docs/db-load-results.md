# Результаты нагрузочных замеров БД

Числа получены из `LoadReportTest` (шаги 337–343, 379–380): тест гоняет сценарии
на реальном PostgreSQL 16 в Testcontainers и печатает отчёт в stdout строкой
`LOADRESULT | <сценарий> | <мс>`. Утверждения в тесте намеренно грубые — проверяется
не скорость конкретной машины, а отсутствие вырожденного поведения.

Бюджеты времени заданы с запасом относительно измеренного на ноутбуке и
масштабируются свойством `-Dstorm.load.budget.factor`: меньше 1 — строже. Жёсткие
миллисекунды в дефолтном прогоне были бы лотереей на загруженном раннере, где
один контейнер Testcontainers обслуживает все тесты сразу.

## Стенд

| Параметр | Значение |
|---|---|
| PostgreSQL | 16.15 (`postgres:16.15-alpine`) в контейнере |
| Пул | Hikari, максимум 6 (тестовый профиль) |
| Настройки сервера | дефолтные контейнера (без compose-параметров: `checkpoint_timeout`, `shared_buffers` и пр. не применялись) |
| Прогон | один JVM, контейнер один на прогон, `TRUNCATE` перед сценарием |

## Результаты

| Сценарий | Время | Комментарий |
|---|---|---|
| 20 000 строк истории одной сессии: чтение | 191 мс | возврат всех строк сессии — худший случай для этой таблицы |
| 10 000 строк журнала: batch insert | 1085 мс | один `batchUpdate`, `rewriteBatchedStatements=on` |
| 10 000 строк журнала: чтение по сессии | 52 мс | рабочий объём одной сессии |
| 5 000 протухших записей кэша: удаление | 20 мс | 3 прохода по 2 000, `SKIP LOCKED` |
| 5 000 протухших записей idempotency: удаление | 36 мс | 3 прохода по 2 000 |
| 200 вопросов: полный цикл записи | 319 мс | сессия + журнал + чтение истории на каждый вопрос |
| очистка 40-дневного журнала: 3 прохода | 20 мс | 5 000 строк, порция 2 000 |

Разброс между прогонами на этой машине — до ±40 % (Docker, общий CPU), поэтому
цифры годятся для порядка величины и для сравнения «было/стало», а не как SLA.

## Что из этого следует

1. **Чистка журналов дешёвая и не блокирует пользователя.** 5 000 строк
   удаляются тремя операторами с `FOR UPDATE SKIP LOCKED`; пока идёт уборка,
   запросы к этой таблице проходят (проверяется тестом «занятая строка
   пропущена, а не ждёт»).
2. **Запись журнала не мешает чтению.** Чтение истории и запись идут по разным
   индексам; `request_log` партиционирована по месяцу.
3. **Партиция месяца важнее индекса.** `default_statistics_target=100` и
   `shared_buffers=256MB` в `infra/compose.yaml` — это стенд, боевой отличается
   памятью; проверять планы надо на боевом хосте, а не на ноутбуке.
4. **Размер батча — это не только скорость.** Порция 2 000 строк выбрана так,
   чтобы одна транзакция уборки не держала длинный WAL и не растягивала
   блокировки (ADR-043).

## Стресс-конкуренция

`PoolSizingAndDeadlockTest`: 30 потоков × 10 операций над сессиями и
`source_state` — без дедлоков и ошибок; `DbPoolStats` показывает, что пул не
превышает `maximumPoolSize`. `IdempotencyConcurrencyTest`: 16 потоков с одним
`requestId` — ровно один победитель, одна строка в `idempotency`.

## Чего эти замеры не доказывают

- Поведение при нескольких нодах: архитектура single-node (ADR-045).
- Поведение на HDD и на медленном диске — только I/O-профиль диска.
- Рост при миллионах строк: ретеншн (`request_log` 30 дней,
  `source_error_log` и `stats_source_hourly` 90 дней) держит журналы в разумном
  объёме, партиции снимают старые месяцы целиком.
- Реальную частоту запросов: модель нагрузки взята из сценариев тестов, а не из
  продакшн-профиля (его ещё нет).
