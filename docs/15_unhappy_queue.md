# Анхэппи пути 76–88: Очередь и нагрузка

> **[ОТМЕНЕНО] Раздел не реализуется в MVP — [ADR-VL-15](decisions.md#adr-vl-15).** Очереди, воркеров и backpressure нет; источники вызываются последовательно, HTTP-клиент один. Все сценарии ниже (переполнение, приоритеты, aging, дедуп в очереди, `RejectedExecutionHandler`, мониторинг очереди, `newVirtualThreadPerTaskExecutor`) либо отменены, либо описывают состояние, которого в MVP не будет.
> Оставлено как материал для будущей задачи, если очередь вернётся. Более ранняя правка ([ADR-VL-05](decisions.md#adr-vl-05)) тоже заменена.

~~Очередь имеет жёсткий лимит + backpressure + приоритеты + aging.~~

### ~~АНП-76. Очередь переполнена~~ — **[ОТМЕНЕНО]** (ADR-VL-15)
1000 запросов в очереди, лимит 500. Новые отклоняются: **429 Too Many Requests + Retry-After: 10**.
Метрика `queue.rejected++`. Alert в Grafana.

### АНП-77. ~~Очередь на OkHttp pool~~ — [ВЛ] Пул один, запросы последовательные (ADR-VL-15)
Пул 5 соединений, 50 запросов ждут. `ConnectionPoolTimeoutException` через 30 сек.
Tool ловит, возвращает пустой с флагом `timeout=true`.
Пользователь видит «Источник не ответил вовремя».

### ~~АНП-78. Очередь на LLM исчерпала timeout~~ — **[ОТМЕНЕНО]** (ADR-VL-15: очередь на LLM не делаем, ADR-VL-03; остаётся таймаут LLM и fallback)
Запрос extract ждёт в очереди >10 сек. Timeout. Fallback: rule-based extractor
(regex + справочник городов). Если и он не справился — Clarifier с общим вопросом.

### ~~АНП-79. Очередь на session store~~ — **[ОТМЕНЕНО]** (ADR-VL-15: своей очереди нет; конкуренция за БД остаётся)
Redis latency 500 мс. 100 параллельных записей. Некоторые таймаутятся. Session не сохраняется.
Пользователь видит ответ, но refine через минуту не работает.
**Ответ:** «Начнём заново».

### ~~АНП-80. Очередь на BZD с cookie-jar~~ — **[ОТМЕНЕНО]** (ADR-VL-15: вызовы последовательные, `Semaphore(1)` на warmup остаётся)
BZD требует warmup-сессию. 20 параллельных запросов, каждый делает warmup.
Warmup-ы конкурируют. Некоторые получают 403. `Semaphore(1)` на warmup — остальные ждут.

### ~~АНП-81. Очередь на SSE Atlas~~ — **[ОТМЕНЕНО]** (ADR-VL-15: SSE-пула нет, вызов последовательный)
5 слотов SSE заняты. 6-й ждёт 15 сек, timeout. Tool возвращает пустой.
Пользователь видит только TicketBus.

### ~~АНП-82. Каскадное переполнение~~ — **[ОТМЕНЕНО]** (ADR-VL-15: очередей, значит каскада переполнения, нет)
Очередь на LLM переполнена → extract timeout → fallback → тоже перегружен → Clarifier →
пользователь пишет → снова в очередь. Замкнутый круг.
**Fix:** hard limit на retry, после 3 попыток — «Сервис перегружен, попробуйте позже».

### ~~АНП-83. Голодание низкоприоритетных задач~~ — **[ОТМЕНЕНО]** (ПРОТ-05 + ADR-VL-15)
Refine с высоким приоритетом постоянно вытесняет новые поиски. Новые поиски не выполняются.
**Fix:** aging — приоритет растёт со временем ожидания.

### ~~АНП-84. Refine в очереди ждёт свежий Atlas, но получает старый кэш~~ — **[ОТМЕНЕНО]** (ADR-VL-01/02: отдельного refine нет; ADR-VL-15: очереди нет)
Пользователь: «Покажи свежие». Refiner: `cache=false`. Tool идёт в Atlas, но Atlas в очереди.
Timeout 10 сек. Fallback: кэш с пометкой «данные могут быть устаревшими».

### ~~АНП-85. Дедупликация в очереди сломалась~~ — **[ОТМЕНЕНО]** (ADR-VL-15: дедуп через `idempotency`, не через очередь)
Два одинаковых запроса не дедуплицировались из-за race condition. Оба идут в Atlas.
Atlas получает 2 запроса вместо 1.
**Fix:** `ConcurrentHashMap<QueryKey, CompletableFuture>` с атомарным `putIfAbsent`.

### ~~АНП-86. Backpressure не сработал~~ — **[ОТМЕНЕНО]** (ADR-VL-15: очереди нет, OOM из-за очереди не бывает)
Очередь растёт до OOM. JVM падает.
**Fix:** жёсткий лимит на размер очереди + `RejectedExecutionHandler`.

### ~~АНП-87. Метрики очереди не собираются~~ — **[ОТМЕНЕНО]** (ADR-VL-15: метрик очереди нет; Prometheus и так не подключаем — ADR-VL-06)
Нет actuator + micrometer (см. общее наблюдение 3). Prometheus не видит очередь. Alert не срабатывает.
**Fix:** добавить зависимости.

### ~~АНП-88. Очередь на виртуальных потоках~~ — **[ОТМЕНЕНО]** (ADR-VL-15: виртуальных потоков нет)
`newVirtualThreadPerTaskExecutor()` без ограничений. 10000 задач создают 10000 виртуальных потоков. Память растёт.
**Fix:** Semaphore или bounded executor.
