## 0.2. Агентный цикл: LLM сам вызывает источники (новое архитектурное решение)

**Что сказал владелец**: «агент должен видеть диалог на протяжении нескольких сообщений; агент сам дёргает API и принимает респонс от всех». Это меняет модель исполнения с фиксированного конвейера на **агентный цикл с инструментами** (function calling).

**Цикл одной реплики**:
```
1. LLM (OpenRouter) получает: системный промпт + история диалога (≤20 сообщений, вся сессия) + список инструментов
2. LLM решает, что искать → возвращает tool_calls: [{tool: "search_bus", args: {...}}, {tool: "search_train", args: {...}}, ...]
3. Агент выполняет вызовы ПОСЛЕДОВАТЕЛЬНО, синхронно, в текущем потоке, и доводит каждый до результата (ADR-VL-15, ПРОТ-01)
4. Результаты (в т.ч. ошибки/таймауты, ПРОТ-04/10/11) уходят обратно в LLM как tool-результаты
5. LLM формирует текстовый ответ пользователю (У-1)
6. Реплика и ответ сохраняются в session_message (У-2)
```

**Инструменты (tools) для LLM** — по одному на источник, чтобы LLM выбирал сам: `search_atlasbus`, `search_ticketbus`, `search_bzd`, `search_ticketpro`, `search_belhotel`; плюс уточняющие: `get_offers` (что нашли), `search_link_options`/`search_accommodation` по флагу.

**Правила**:
- Инструменты — только источники; БД/LLM наружу не выдаём.
- Каждый источник максимум 1 вызов за раунд (анти-повторы), при повторе — возвращаем пояснение.
- Ошибка источника — не прерывает цикл: в tool-результате `{status: FAILURE, code, message}`.
- Число раундов — **решает агент**: лимит приходит из настроек агента (`AgentProperties.llm.maxToolRounds`, по умолчанию 2) и дублируется в системном промпте («не более N раундов поиска»); жёсткой остановки в коде нет, при достижении лимита цикл завершается и LLM отвечает по имеющимся данным. Позже тем же способом лимит будет настраиваться для агента на n8n.
- История диалога — всегда целиком (макс. 20 сообщений, В-12).
- **LLM-ключа пока нет** (В-14) → в коде `LlmGateway` с провайдером OpenRouter и `OPENROUTER_API_KEY`/`OPENROUTER_MODEL` из env; пока ключа нет, работает fallback: тот же цикл выполняется с локальным «решателем» по правилам, который выбирает источники по флагам/контексту и собирает текст из офферов. Архитектура и тесты одни и те же — меняется только реализация шага решения.

**Модель оффера в MVP (В-10)**: **цены и тарифы подробно, остальное — минимум**: `from`, `to`, `date/time`, `price`+`currency`+кол-во билетов, `tariffName`/`class` (например «эконом», «купе»), `source`, `kind`, `url`/`externalId`. Всё остальное из доков (`attributes`, `baggage`, `documents`, `cancellation`, `transfers`) — **не парсим** (помечено «после MVP»).

## 0.3. Решение владельца (раунд 3): всё синхронно, один клиент, без очереди

**Что сказал владелец**: «без воркеров пока, отмени все пункты, которые с этим связано. надо один `httpClient`, агент должен синхронно дёргать все запросы». Зафиксировано как [ADR-VL-15](decisions.md#adr-vl-15).

| ПРОТ | Было (раунды 1–2) | Стало (ADR-VL-15) |
|---|---|---|
| 01 | Параллельный fan-out, ждём всех, каждый источник ограничен своим таймаутом | **Последовательный** вызов источников в порядке от LLM, в потоке HTTP-запроса; каждый доводится до конца |
| 03 | Несколько `OkHttpClient` (`newBuilder()`, SSE-клиент, тяжёлые POST) ради параллелизма | **Один** `OkHttpClient` на приложение, общий набор таймаутов; `callTimeout` — явно, не `0` |
| 04 | Backpressure: 503 + `QUEUE_REJECTED` + `Retry-After: 5`, лимит 100 | Очереди нет — значит нет и backpressure-ошибок; `QUEUE_REJECTED` в enum остаётся, но не выдаётся; `429` — только rate limit пользователя |
| 05 | Простая FIFO `ArrayBlockingQueue(100)` + 4–8 воркеров | Очередь и воркеры **отменены** полностью; backpressure обеспечивает сам Tomcat |
| 06 (У-6) | Пул + `ArrayBlockingQueue(100)` | Отменено; запрос обслуживается в своём потоке |
| У-7 | Отмены запроса нет | В силе: отмен нет и дочерних потоков |
| В-8 | per-source таймауты + alert + ручной флаг `enabled` | Таймауты **одного** клиента + alert + ручной флаг `enabled` |

**Что отменено из MVP**: `RequestQueue`, `RequestTask`, `QueueProperties`, `BackpressurePolicy`, consumer pool, `ParallelExecutor`, виртуальные потоки/`ExecutorService`/`CompletableFuture`, производные `OkHttpClient`, семафоры на источники, `QueueMonitor`, метрики `queue.*`, `QUEUE_REJECTED`/`Retry-After` для очереди, health-проверка очереди, сценарии `13`/`15`/`09`/`11` по очередям и параллелизму.

**Что остаётся**: `request_log` (аудит), дедупликация `requestId` через таблицу `idempotency` (ADR-001), последовательный `SourceExecutor`, кэш с TTL 5 мин (снимает худший случай — сумму таймаутов), планировщики на БД (тёплый кэш/warmup/housekeeper) — они не пул источников.

**Цена решения (зафиксирована осознанно)**: худший случай = сумма таймаутов источников подряд. Поэтому таймауты короткие, кэш обязателен, а вопрос per-source таймаутов и параллельного fan-out вынесен в отложенные вопросы `decisions.md` (ADR-VL-15) — вернуться, когда появятся реальные данные о нагрузке.

## A. Таймауты, последовательность вызовов, один клиент

### ПРОТ-01. Per-source таймаут 60 с не помещается в request deadline 15 с — `Блокирующий` — `ЗАМЕНЕНО (ADR-VL-15)`
- **Ссылки**: `23_impl_blueprint.md:317` («connect 5s, read 10s (**bzd/ticketbus: 60s** для тяжёлых POST), SSE read 10s + max duration 30s, **callTimeout 45s**, общий deadline запроса = `deadlineMs` из `SearchRequest` (**default 15s**), бюджет на источники = 90 %») vs `23:318` (fan-in ждёт до deadline) vs `17:74` («Read timeout — 10 сек») vs `22:79` vs `24:31` (АДР-010).
- **Решение владельца (раунд 1)**: ждём, пока выполнятся **все** запросы. Общего «обрыва» по 15 секунд нет.
- **[ВЛ] Уточнение раунда 3 (ADR-VL-15)**: «все» значит **последовательно**, а не параллельно. Никакого fan-out/fan-in, `CompletableFuture.allOf` и дочерних потоков нет.
- **Как реализуем**: `SourceExecutor.execute(calls)` — цикл по списку вызовов в порядке от LLM, каждый вызов синхронно в текущем потоке; ограничение даёт таймаут **одного общего** клиента (connect 5 с, read 10 с, `callTimeout` — явно, не `0`). LLM — отдельной фазой (ПРОТ-02). Поле `deadlineMs`, если где-то осталось, — **advisory** (в лог/метрику), ничего не обрывает; отмены нет.
- **Цена**: худший случай = сумма таймаутов подряд. Смягчается кэшем (TTL 5 мин) и короткими таймаутами; вопрос per-source таймаутов отложен в `decisions.md` (ADR-VL-15).

### ПРОТ-02. LLM timeout 30 с > deadline запроса 15 с — `Средний` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`
- **Ссылки**: `07:15` («висит **30 сек**») vs `13:17-18` (очередь LLM **до 5 сек**, дальше rule-based) vs `23:126` (`deadlineMs: 15000`).
- **Решение владельца**: сначала выполняются и собираются запросы к источникам, **затем** LLM. Отдельного общего 15-секундного окна нет.
- **Как реализуем**: `SearchOrchestrator`: `tools → combine/rank → LLM summary` строго последовательно; таймаут LLM — 30 с (АНП-31), при таймауте — шаблонное summary («Найдено N вариантов, лучший — X», `07:16`). [ВЛ] ~~Очередь/rate-limit LLM остаётся~~ — **отменено** (ADR-VL-15): своей очереди нет; остаётся только таймаут LLM 30 с и rule-based fallback.
- **Что переписать**: `23:317` (LLM в бюджете 90 %) убрать; в плане фаза LLM — после оркестрации, а не внутри шага вызова источников.

### ПРОТ-03. «Единственный OkHttpClient» + per-source таймауты vs API OkHttp и пул в 5 соединений — `Блокирующий` — `ЗАМЕНЕНО (ADR-VL-15)`
- **Ссылки**: `24:29` (АДР-008) vs `23:316` («каждому потоку присваивается свой `OkHttpClient`-таймаут») vs код `AppConfig.java:12-31` (один клиент), `OkHttpProperties.java` (`callTimeoutMs=0`, `maxIdleConnections=5`), `application.properties` vs `23:317` (`callTimeout 45s`) vs `13:8`, `13:46` (пул **5**, SSE держит 5–10 с), `15:27-29` (АНП-81: 6-й SSE ждёт и уходит в timeout).
- **Решение владельца (раунд 1)**: несколько `HttpClient` разрешены ради параллелизма.
- **[ВЛ] Решение раунда 3 (ADR-VL-15)**: **один** `HttpClient` на всё приложение. Производные клиенты (`newBuilder()`), отдельный SSE-клиент, per-source профили и `Semaphore`-слоты **отменены** — параллелизма, который они обслуживали, больше нет.
- **Как реализуем**:
  1. Один `OkHttpClient` из `AppConfig`/`OkHttpProperties` — как сейчас в коде, без изменений.
  2. Общий набор таймаутов: connect 5 с, read 10 с, write 10 с; `callTimeout` — задать явно (в коде сейчас `0` = бесконечно), не `0` и не 45 с.
  3. Пул соединений 5, keep-alive 5 мин — остаётся (ADR-015); при последовательных вызовах этого достаточно.
  4. Источники, требующие иных таймаутов (SSE, тяжёлые POST), — либо укладываются в общий таймаут, либо вопрос per-source таймаутов решается отдельно (отложен в `decisions.md`, ADR-VL-15).

### ПРОТ-04. Backpressure: 429/503 и три разных порога — `Средний` — `ЗАМЕНЕНО (ADR-VL-15): очереди нет
- **Ссылки**: `13:29` (>100 → **429** + `Retry-After: 5`) vs `15:6` (лимит **500** → **429** + `Retry-After: 10`) vs `16:93` (`queue.reject` → **503**) vs `23:372`, `23:485` (`QUEUE_REJECTED` → 503) vs `23:483` (лимит 100) vs `24:27`.
- **Правило владельца (п. 04)**: если какой-то запрос упал — **сообщить об этом в сообщении пользователю**. Это касается не только очереди: каждый упавший источник попадает в `warnings` ответа и в текст summary («Atlas временно недоступен» — `05:8`), ответ — HTTP 200 с `partial=true` (`23:208`).
- **Решение по backpressure (раунд 1)**: 503 + `QUEUE_REJECTED` + `Retry-After: 5`, лимит очереди 100.
- **[ВЛ] Раунд 3 (ADR-VL-15)**: очередь отменена, поэтому спор о порогах снят. `QUEUE_REJECTED` остаётся в `ErrorCode`, но **никогда не выдаётся**; `Retry-After` в ответе не возвращается; alert по `queue.length` отменён. `429` (`TOO_MANY_REQUESTS`) остаётся только для rate-limit по пользователю (`10:8`). Правило п. 04 (упомянуть упавший источник в тексте ответа) — в силе и теперь единственное, что регулирует частичные результаты.

### ПРОТ-05. Очередь: приоритеты и aging в доках vs решение «простая FIFO» — `Высокий` — `ЗАМЕНЕНО (ADR-VL-15): очереди нет

**Простыми словами.** Очередь — «прилавок», где ждут задачи. Требования из доков были сложными:
- **Приоритет**: refine («подешевле», «только Atlas») — короткий, часто из кэша → высокий приоритет (`13:25`, `13:73`); новый полный поиск — обычный; фоновое обновление кэша — низкий (`23:484`).
- **Старение (aging)**: задача, пролежавшая долго, сама поднимается в приоритете, иначе refine-запросы вечно вытесняли бы новые поищи и они «голодели» бы (`15:36-38`, АНП-83).
- **Жёсткий лимит**, дедупликация, отмена — из `23:483-487`, `15:44-47`, `08:38`.

**Решение владельца (раунд 1)**: очередь **простая, FIFO — кто раньше, тот и выполняется**. Никаких приоритетов и старения.

**[ВЛ] Решение раунда 3 (ADR-VL-15) — вопрос снят целиком: очередь отменена.** Противоречие «в доках приоритеты и aging, в решении простая FIFO» больше не существует: нет ни очереди, ни приоритетов, ни aging, ни воркеров.

**Как реализуем**:
- `RequestQueue`/`RequestTask`/`QueueProperties`/`BackpressurePolicy` — **не строим**; consumer pool 4–8 (`23:487`) — **не строим**.
- Запрос обслуживается в потоке HTTP-запроса: контроллер → `SearchOrchestrator` → инструменты последовательно → ответ.
- Нагрузку ограничивает сам Tomcat числом потоков; отдельная backpressure-ошибка не нужна.
- Отмена пользователем (`08:38`) — неактуальна и так (У-7, ADR-VL-09).
- Дедупликация одинаковых `requestId` (`23:486`) остаётся, но делается **таблицей `idempotency`** (ADR-001), а не очередью.
- Метрики `queue.length`, `queue.wait_ms`, `queue.rejected` (C20) — отменены; `QueueMonitor` не строим.
- `13_happy_queue.md` и `15_unhappy_queue.md` помечены `[ОТМЕНЕНО]` целиком и остаются справочными.

**Что убрано из доков**: `13:25-26` (приоритет, `PriorityBlockingQueue`), `13:73`, `15:36-38` (АНП-83, голодание/aging), `23:484` — плюс сами разделы очереди в `13`/`15`/`16`/`23 §12`. Побочный эффект: АНП-83 («низкоприоритетные задачи голодают») неприменима — задач в очереди нет.

## B. Circuit breaker, флаги источников, сессии

### Про breaker: что он даёт и почему его пока не делаем

Источник (например Atlas) может упасть или начать блокировать наши запросы (анти-бот, 500-ки).
**Без breaker** каждый пользовательский запрос снова стучится в мёртвый источник:
- пользователь ждёт таймаут источника (10–30 секунд) вместо быстрого ответа;
- источник видит лавину запросов и может заблокировать нас по IP → перестанет работать совсем (ошибки 207, 219).
**С breaker** после 5 ошибок за 30 секунд источник помечается «не работает» на 60 секунд: отвечаем мгновенно кэшем/пустотой с сообщением («Atlas временно недоступен», `05:8`), потом одна проба.

**Решение владельца: «пока без breaker».** Что делаем вместо:
1. Упал источник → `PrincipalResult(FAILURE, ...)` + **сообщение пользователю** (п. 04) + метрика + запись WARN.
2. Таймауты клиента (ПРОТ-01/03) — чтобы не ждать бесконечно; общий набор, один `OkHttpClient` (ADR-VL-15).
3. `AlertEvaluator` + лог при N ошибках подряд (`source.errors` за окно) — сигнал, что пора чинить; порог в конфиге, без автоматического отключения источника.
4. Ручное отключение источника — админ-флаг `enabled` (`source_state`) за `X-Api-Key` (ПРОТ-26).
5. Circuit breaker — отдельная задача; вернуться, когда появятся реальные данные о падениях/банах.

### ПРОТ-06. TTL сессии: 1 час / «2 часа» / 30+15 мин — `Средний` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`
- **Ссылки**: `08:15` (вернулся через 2 часа → истекла) vs `14:4` («Session TTL **1 час**») vs `23:429` («**BZD 30 мин**, idle 15 мин») vs `24:307` (30 мин актив / 15 мин idle).
- **Решение владельца**: сессия активна **15 минут**; интерфейс и устройство сессии — **как чат-бот**.
- **Как реализуем**: один TTL = **15 минут с последнего обращения** (продлевается каждым запросом — `24:174`, `24:821` `touch()`); отдельного «активного» TTL нет. В `SessionProperties` (`24:285`, `23:84`) одно поле `sessionTtlMinutes=15`. «BZD 30 мин» в `23:429` — опечатка (смешение с cookie BZD, `19:61`).
- **Сессия как чат**: сессия = диалог (см. состав в ПРОТ-07) — список сообщений пользователя и ответов агента в хронологическом порядке + текущий интент. API отдаёт/принимает историю сообщений (`В-7`).

### ПРОТ-07. Где хранить circuit-состояние и флаги источников: память / Redis / БД — `Блокирующий` — `РЕШЕНО ВЛАДЕЛЬЦЕМ` (+ пояснение)
- **Ссылки**: circuit in-memory `23:436-458`; флаг «в БД `source.atlas.enabled=false`» — `16:60`; session store — Redis/Caffeine `13:38`, Redis-latency `15:19`, «сессии в Redis» `16:102` vs `23:472` («`ConcurrentHashMap` (или Redis, **если появится зависимость**)») vs план `24:26` (АДР-005), `24:183` (circuit в БД), `24:401` (ADR-044), `24:403` (ADR-045, single-node).
- **Владелец спросил: «что включает в себя сессия?»** и уточнил: **«интерфейс как чат-бот»**. Состав сессии (диалог + состояние):
  0. **история сообщений (чат)**: `[{role: user|agent, text, createdAt, requestId, kind}]` в хронологическом порядке — как обычный чат-бот: что написал пользователь, что ответил агент (`12:90` «сохраняет историю сообщений для контекста», `14:20`, `13:7`);
  1. `id` сессии;
  2. **текущий интент**: домены, `from`/`to`, даты, пассажиры, пожелания, бюджет+валюта, сортировка, окна времени, флаги (`directOnly`, `sources`, `linksOnly`) — то, что refine меняет (`12:1-108`, `23:474-476`);
  3. **история шагов refine**: что именно меняли и в каком порядке («подешевле» → «только Wi-Fi» → …), чтобы «откатить»/объяснить (`14:30-33`, `24:176`);
  4. **выбранный вариант** (`selectedOption`, `12:97`) и «остальные отброшены» (`12:98`);
  5. **снимок последнего результата** — чтобы «покажи то же самое» / «покажи предыдущий вариант» отвечали без новых запросов к источникам (`14:20`, `12:94-95`);
  6. **последний `requestId`** — защита от двойного submit/идемпотентности (`23:502`);
  7. **время**: `createdAt`, `lastAccessAt`, TTL (`23:475`, `24:173`);
  8. **служебное**: `state` (`NEW|ACTIVE|EXPIRED|CANCELLED` — `24:173`, `08:45` «отмена»).
  Не входит: сами офферы (транзитные, ADR-032 `24:202`) и сырой текст промпта (в `request_log`, `24:270`).
- **Решение**: хранение — **Postgres** (`session`, `session_refine`, `session_message` — `24:173-177`, `source_state`). In-memory — копия для чтения (только флаги источников, TTL 30 с — `16:114`). Redis не добавляем. `13:38`/`15:19`/`16:102` переписать: сценарии деградации при недоступной БД, не Redis. Таблица `circuit_state` (`24:181-182`) **не заводится** — breaker отменён.

### ПРОТ-08. TTL OPEN: 60 с или 5 мин — `Средний` — `ОТМЕНЕНО` (breaker не делаем)
- **Ссылки**: `16:9-10`, `16:14`, `22:54` (OPEN на **60 с**) vs `16:38` («TTL на OPEN — **5 мин**, потом принудительный HALF_OPEN») vs `23:427`, `23:442` (`openTimeoutMs=60_000`), `23:458` (force-макс 5 мин).
- **Простыми словами** (для будущего): breaker — «предохранитель» на источник. Источник начал падать (5 ошибок за 30 с, `22:54`) → breaker открывается: в источник не идём, отдаём кэш/пустоту с предупреждением. Через какое время пробовать снова? Спека: **60 секунд**; один анхэппи-путь: **5 минут** (страховка от «залипшего» breaker, АНП-96). При возврате breaker к вопросу — 60 с норма, 5 мин потолок (`23:427/458`).
- **Решение владельца**: **пока без breaker** → обе цифры отложены. Фазы circuit breaker в `24` пропускаются, `23 §10` не реализуется.

### ПРОТ-09. `enabled=true` сбрасывает circuit или нет + разная гранулярность ключей — `Высокий` — `ОТМЕНЕНО` (breaker не делаем)
- **Ссылки**: `16:65` (АНП-102: «при `enabled=true` принудительно CLOSED») vs «circuit > enabled» — `README:103`, `16:117` (АНП-115), `23:57`, `23:457`; гранулярность: circuit key = `source:endpoint` (`23:444`, АНП-97 `16:41`), флаг — на источник (`16:60`).
- **Простыми словами** (для будущего): источник можно заблокировать двумя способами — флагом `enabled` (человек выключил на обслуживание) и breaker (источник сам падает). Правило README: важнее breaker. АНП-102: при включении обратно breaker сбрасывают — иначе после 10 минут обслуживания источник остался бы выключенным. При возврате breaker — сбрасывать только при `opened_by=MANUAL`.
- **Решение владельца**: остаётся **только ручной флаг** `source_state.enabled` (без кэша circuit, без `opened_by`); вопрос сброса отпадает.

### ПРОТ-10. Retry и счётчик ошибок — `Высокий` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`
- **Ссылки**: `22:66` («счётчик ошибок **учитывает и retry-попытки**») vs `16:44-46` («1 пользовательский запрос = 1 ошибка») + `23:456`; объём retry: `16:45` («Client делает **retry 3 раза**») vs `22:62-66` («по умолчанию retry отсутствует»).
- **Решение владельца**: «3 ретрая — это ошибка» ⇒ внутри одного запроса повторы **не** увеличивают счётчик ошибок; 1 запрос = 1 ошибка (или 0, если запрос в итоге успешный).
- **Как реализуем**: счётчик ошибок источника (для метрик и alert-порога) считает результат **пользовательского** запроса, а не попыток. Разрешённые повторы — только из `22:62-66`: connection reset (1 раз), warmup (1 раз, но с учётом п. 11 — только для 401); 503/429 — без retry (ПРОТ-12). Формулировку `22:66` исправить.

### ПРОТ-11. Политика 403: circuit OPEN / warmup-retry / тихий пустой список — `Высокий` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`
- **Ссылки**: `17:26` (403 → circuit OPEN) + `22:58` vs `05:24-25` (АНП-15: BZD 403 → повторный warmup, затем пустой список) vs `19:87-88` (ошибки 87/88: протухшая cookie → retry warmup) vs `22:37` (401 → retry warmup).
- **Решение владельца**: при 403 **сообщаем пользователю и не повторяем** (никакого warmup-retry на 403).
- **Как реализуем**: 403 (403/403-капча/anti-bot) → `PrincipalResult(FAILURE, SOURCE_FORBIDDEN)` + сообщение пользователю + метрика `source.errors{source,code=403}` + alert «анти-бот/бан» (`22:99`). Без breaker следующий запрос попробует источник снова — поэтому важен alert и ручное отключение флагом. 401 → один warmup (`22:37`) — это не 403. Тексты `05:24-25` и `19:87-88` в части «повторить warmup на 403» устарели; `17:26` и `22:58` (403 → circuit OPEN) — отменяются.

### ПРОТ-12. «Пауза источника на N сек» (503/429) — `Средний` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`
- **Ссылки**: `17:16` (ошибка 3), `17:22-23` (ошибка 5), `22:33-35` («пауза источника на N сек») vs `23 §10` (в breaker только CLOSED/OPEN/HALF_OPEN — места для паузы нет).
- **Решение владельца**: **паузы не делаем** — механизма `pausedUntil`/cooldown не будет.
- **Как реализуем**: 429/503 → сразу `PrincipalResult(FAILURE, SOURCE_RATE_LIMITED / SOURCE_UNAVAILABLE)` + сообщение пользователю + метрика + alert при повторах. Ни паузы, ни breaker — источник пробуем снова на каждом запросе. Строки `17:16`, `17:22-23`, `22:33-35` помечаем как отменённые.

## C. Данные и модель

### ПРОТ-13. Идентификаторы источников: `atlas` vs `atlasbus` + обязательные интерфейсы — `Средний` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`

Ключи вида `source:endpoint` остаются только для метрик (без circuit-состояния).

### ПРОТ-14. Валюта: конвертировать в BYN или исключать из сортировки — `Средний` — `РЕШЕНО` (на усмотрение)
- **Ссылки**: `23:334` (котировки в Constants) vs `23:507` (`currencyKnown=false` → не участвует в сортировке) vs `10:39` (АНП-54) vs `21:227` vs `19:129` (ошибка 103: BYN и RUB).

### ПРОТ-15. Часовой пояс: UTC vs Europe/Minsk — `Средний` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`
- **Ссылки**: `24:35` (ADR-016: `timestamptz`, всё в UTC) vs `23:287` («TZ **Europe/Minsk**») vs `23:158-159` (`+03:00`) vs `19:126` (ошибка 108) vs `21:92` (ошибка 228) vs `02:8` (стыковка «≥2 часа»).
- **Решение владельца**: **Europe/Minsk**.
- **Как реализуем**: все расчёты, стыковки, окна времени, агрегация по часам — в `Europe/Minsk` (`24:251`, ADR-035, границы суток — минские); в БД `timestamptz` (технически UTC — ADR-016 остаётся, это деталь хранения), но **все** сравнения и форматирование — Minsk. Ответ API отдаёт `+03:00`. Стыковка «2 часа до концерта» (`02:8`) считается в минском времени. `21:92` (Europe/Moscow) — только предупреждение для РФ-маршрутов.

### ПРОТ-16. «Отель рядом с venue»: ≤1 км / 2 км / «15 км — далеко» — `Низкий` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`

- **Решение владельца**: **1 км**. Значение — в настройках агента (`AgentProperties.nearVenueMeters=1000`), можно менять без кода.

### ПРОТ-17. Размер выдачи: 20 / top-50 / top-3 комбо / пагинация по 5 — `Низкий` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`
- **Ссылки**: `23:127` (`maxOffers: 20`), `23:333`, `05:56` (топ-20 + top-3 комбо), `06:27` (top-50), `02:31` (4 комбо), `12:7-8` (`offset += 5`).

Значения читаются из конфига — расхождения примеров (`02:31`) снимаются.

### ПРОТ-18. Модель `prefs.sort` не выражает мульти-сортировку — `Низкий` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`
- **Ссылки**: `23:146` (`sort` — одно значение) vs `14:43-45` (АНП-73: «и дешёвый, и быстрый»).
- **Решение владельца**: **спросить пользователя** (Clarifier: «Что важнее — цена или время?», `14:45`). Вариант «последний выигрывает» (`14:44`) удаляем; `sort` остаётся одиночным значением.

### ПРОТ-19. «Ничего не нашлось» vs «все источники недоступны» — `Средний` — `РЕШЕНО` (на усмотрение) + п. 04
- **Ссылки**: `05:17` vs `23:369` (`ALL_SOURCES_UNAVAILABLE`) vs `19:115` (200 с 0 результатов — легитимно).
- **Решение**: различать по `PrincipalResult.status`: все `OK` с 0 → «ничего не нашлось» + предложение изменить запрос; есть `FAILURE/TIMEOUT/SKIPPED` → `ALL_SOURCES_UNAVAILABLE`; **в обоих случаях перечисляем упавшие источники в сообщении** (правило владельца, п. 04). HTTP 200 в обоих случаях (`23:208`).

### ПРОТ-20. Имена метрик: `type` vs `code`, без тегов — `Низкий` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`

### ПРОТ-21. Prometheus: добавлять зависимость или «не добавлять» — `Средний` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`

- **Решение владельца**: **пока не добавляем**.
- **Как реализуем**: метрики — собственные счётчики `MetricsCollector` + пороги `AlertEvaluator` с записью в лог WARN (`23:496`); `/actuator/prometheus` и `micrometer-registry-prometheus` **не подключаем**. Внутренние эндпоинты диагностики (`24:304`, `/api/v1/diagnostics/slow-queries`) закрываем `X-Api-Key` (ПРОТ-26).

### ПРОТ-22. Порядок фаз: 13 фаз без БД (23) vs БД-first (24) — `Высокий` — `РЕШЕНО ВЛАДЕЛЬЦЕМ`
- **Ссылки**: `23 §15` (0–12, БД отсутствует) vs `24:36` (АДР-013: БД → исключения → модель → гейтвеи → circuit → параллельность → …).
- **Решение владельца**: «остальные — на своё усмотрение» ⇒ оставляю **порядок плана** (БД-first), `23 §15` считается устаревшим в части БД/очереди/сессий. Фазы circuit breaker (`24`, `23 §10`) — **пропускаются** по решению владельца (ПРОТ-08/09).
- **Что помечаем в `23` как заменённое планом**: §10 (circuit in-memory), §11 (SessionStore in-memory), §6.2 (60 с / callTimeout 45 с / budget 90 %), §13 (Prometheus). §12 раньше заменялся на «`ArrayBlockingQueue(100)` FIFO без приоритетов/aging», но **[ВЛ] раундом 3 (ADR-VL-15) §12 отменён целиком**: очереди нет; `13:25-26`, `13:73`, `15:36-38` сняты вместе с ней.

### ПРОТ-23. АНП-41 (Jackson 2 vs 3) — `Средний` — **подтверждено кодом (баг)**
- **Ссылки**: `09:13-17` vs код: `entity/atlas/AtlasRide.java:6-7`, `entity/atlas/AtlasBookingAvailability.java:6-7` — `com.fasterxml.jackson.annotation.*` (Jackson 2), парсеры — `tools.jackson.*` (`jackson.version=3.1.5` в `pom.xml`).
- **Следствие**: `@JsonProperty`/`@JsonIgnoreProperties` из Jackson 2 **игнорируются** Jackson 3 → поля молча не маппятся (например `carrier_phones`), как описано в АНП-41.
- **Решение**: фикс из `09:17` — перевести импорты на `tools.jackson.annotation`, плюс тест «обязательные поля маппятся» (АНП-41 Guard, `09:16`).

### ПРОТ-24. `@ResponseStatus(BAD_GATEWAY)` на исключениях vs «убираем» — `Средний` — **подтверждено кодом**
- **Ссылки**: `23:17` и `23:354` («аннотация **убирается**, статус навешивает `GlobalExceptionHandler`») vs код: 9 классов с `@ResponseStatus(HttpStatus.BAD_GATEWAY)` (`exception/AtlasClientException.java:6`, `AtlasServiceException`, `BzdClientException`, `TicketBusClientException`, `TicketBusServiceException`, `TicketProClientException`, `TicketProServiceException`, `BelHotelClientException`).
- **Решение**: следовать `23:354` — убрать аннотации при вводе `StormException`/`GlobalExceptionHandler` (фаза 1, шаги 48–51). Иначе наружу утечёт 502 вместо `ErrorCode` (`23:208`).

### ПРОТ-25. Доки предполагают сервис-слой для BZD и BelHotel, которого нет — `Низкий` — `РЕШЕНО`
- **Ссылки**: `05:25` (АНП-15: «**Service** пробует warmup ещё раз»), `05:38`, `19:56-120` vs код: сервисы есть только `AtlasService`, `TicketBusService`, `TicketProService`; `BzdService`/`BelHotelService` **нет** (warmup внутри `BzdClient.java:50,64,95-102`).
- **Решение**: warmup/retry-логику держим в гейтвеях (`BzdGateway`, `23 §5.3`) + `WarmupScheduler` (`23 §9`); новые сервис-классы не заводим (меньше кода, совпадает с `23 §5.3`). Тексты `05:25` переформулировать.

### ПРОТ-26. Админ-эндпоинты включения/выключения источников без авторизации — `Средний` — `РЕШЕНО` (на усмотрение)
- **Ссылки**: `23:109-110` (`POST /api/v1/sources/{name}/enable|disable`) — аутентификации нет; `24:304` (`/api/v1/diagnostics/slow-queries`, админ) — тоже; `21:202-203` (юридические риски неконтролируемого использования) vs `24:74` (CORS без auth).
- **Решение**: закрыть `/api/v1/sources/**` и `/api/v1/diagnostics/**` заголовком `X-Api-Key` (значение из env `STORM_ADMIN_KEY`, при отсутствии — приложение стартует, но эндпоинты отвечают 401) + CORS-whitelist (`24:74`). Ключ не в репозитории (шаг 28, `24:382`).

## E. Политики и право (на усмотрение владельца)

### ПРОТ-27. Обход анти-бота vs robots.txt / ToS — `Средний` — `РЕШЕНО` (на усмотрение)
- **Ссылки**: `21:201-203` (уважать `robots.txt`; ToS/Cease&Desist → **отказ**) vs `21:206` (headless с «реалистичным fingerprint»), `21:217-218` (бан по JA3/HTTP-2 → **uTLS / curl-impersonate**), `21:213-214` (гео/VPN → прокси в РБ / residential), `19:80` (Cloudflare → headless), `20:124` (reCAPTCHA → headless), `19:92` (ошибка 92: BZD `_ga` → headless или отказ), `20:150` (JS-редирект → headless).
- **Решение**: для МВП — **без обхода**: уважаем `robots.txt`, не используем uTLS/имперсонацию/прокси/headless. При анти-боте: `PrincipalResult(FAILURE, SOURCE_FORBIDDEN)` + alert «источник под анти-ботом» (`22:99`), пользователю — сообщение; дальше источник отключают вручную флагом `enabled` (breaker отменён, ПРОТ-08). Headless-браузер и прокси — отдельное АДР, если владелец позже подтвердит легальность.
- **Следствие для плана**: не заводить headless/прокси-зависимости; ошибки 53, 54, 57, 58, 80, 92, 124, 150, 206, 217, 218 закрываются как «источник недоступен», а не как «обойти».
