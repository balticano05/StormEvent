# Ретеншн и чистки

Кто чем чистит, с какой частотой и в каком порядке. Значения TTL задаёт
приложение (ADR-038), база только хранит и индексирует.

## Сроки хранения

| Данные | Срок | Способ |
|---|---|---|
| `session` | 15 минут с последнего обращения | `expires_at` + `findExpiredIds(…, limit)` + `deleteByIds` |
| `session_message` | вместе с сессией | `ON DELETE CASCADE` |
| `cached_result` | индивидуальный `expires_at` источника | `findExpiredKeys(…, limit)` + `deleteByKeys` |
| `idempotency` | 5 минут | `findExpiredIds(…, limit)` + `deleteByIds` |
| `request_log` | 30 дней | `DROP` месячной партиции, `deleteOlderThan` добор |
| `source_error_log` | 90 дней | `DROP` месячной партиции, `deleteOlderThan` добор |
| `stats_source_hourly` | 3 месяца | `DROP` месячной партиции |
| `request_log` для истёкшей сессии | не удаляется | сессия обнуляет ссылку, строка остаётся |

## Порядок прохода

1. **Сессии.** `SELECT id ... WHERE expires_at < now() ORDER BY expires_at
   LIMIT :batch` → один `DELETE ... WHERE id IN (...)`. Каскад уносит реплики
   диалога.
2. **Кэш.** `SELECT cache_key ... WHERE expires_at < now() LIMIT :batch` →
   один `DELETE`. Просроченное, но годное отдаётся как `stale`, из базы
   уходит штатно.
3. **Дедупликация.** Тот же путь: `findExpiredIds` + `deleteByIds`.
4. **Журналы.** `DELETE ... WHERE created_at < :cutoff` — только добором;
   основной путь — удаление партиций.

Размер порции задаёт `storm.db.cleanup-batch` (по умолчанию 2000), а не
константа в коде: на одной ноде с 1 GB памяти большая порция держит
транзакцию и блокировки дольше, чем даёт выигрыш в числе операторов.

### SKIP LOCKED

Чистки **не блокируют** пользовательские операции. Идентификаторы
выбираются с `FOR UPDATE SKIP LOCKED`, поэтому строка, которую в эту секунду
трогает запрос пользователя, не блокирует housekeeper и не ждёт его: она
просто попадёт в следующий проход.

`DELETE ... LIMIT` в PostgreSQL не существует, а `EXISTS` в целевом списке
`UPDATE`/`DELETE` не поддерживается — отсюда форма `IN (SELECT … LIMIT …
FOR UPDATE SKIP LOCKED)` (ADR-043). Индексы при этом работают: выборка идёт
по индексам, а не по последовательному сканированию (`IndexUsageTest`).

### Бюджет операторов

5 000 строк журналов чистятся за три прохода, но в проходе два оператора
(журнал запросов и журнал ошибок) — итого 8 операторов, а не «6» из
первоначальной оценки. Тест фиксирует именно этот бюджет, чтобы
регрессия по числу запросов ловилась, а не «помногилось на глаз».

Один проход идемпотентен: повторный ничего не удаляет и не падает на пустом
результате (проверено `RetentionCleanupTest`).

## Месячные партиции

`request_log`, `source_error_log` и `stats_source_hourly` партиционированы по
времени (ADR-033). В схеме есть `DEFAULT`-партиции: если месячная партиция не
создана, запись уходит туда и ничего не теряется.

Партиции создаёт не миграция, а код — `PartitionMaintenance`:
`ensureUpcoming` создаёт партиции на `storm.db.partition-months-ahead` месяцев
вперёд. Причина в [ADR-044](../docs/decisions.md): конфигурация БД живёт в
трёх слоях (compose → initdb → Flyway), и таблицы, создаваемые во время работы
приложения, Flyway не видит.

`dropOlderThanRetention` удаляет целые месячные партиции старше срока
(`DROP TABLE`, метаданные, мгновенно) и только потом добирает остаток
`deleteOlderThan` — строки, попавшие в `DEFAULT`-партицию или в партицию
«слепого месяца».

```sql
-- создать партицию на месяц вперёд
CREATE TABLE storm.request_log_2026_11 PARTITION OF storm.request_log
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

-- убрать старый месяц вместо DELETE по строкам
DROP TABLE storm.request_log_2026_08;
```

Порядок важен: партиция создаётся **до** начала месяца, `DROP PARTITION` —
**после** того, как месяц вышел за retention. `DEFAULT`-партиция остаётся
последним рубежом: если партицию не создали, запись не падает, а попадает в
`_default`, и это видно в метриках размера партиций.

### Расписание

Партиции и журналы обслуживает `DbMaintenanceScheduler`:

| Задача | Расписание | Что делает |
|---|---|---|
| Партиции | `0 10 3 * * *` | создаёт партиции вперёд, удаляет месяцы за retention |
| Ночная уборка | `0 0 4 * * *` | полный проход: истёкшее плюс журналы |
| Дневная уборка | `0 0 * * * *` | только истёкшее: сессии, кэш, дедупликация |

Часы задаются свойствами `storm.db.maintenance.partition-cron`,
`storm.db.maintenance.nightly-cron` и `storm.db.maintenance.hourly-cron`.
Общее выключатель — `storm.db.maintenance-enabled`; в профиле `test` он
выключен, потому что контейнер Postgres общий на весь прогон, а фоновые
партиции меняют число таблиц и планы запросов у соседних тестов.

При старте приложения (`ApplicationReadyEvent`) партиции создаются сразу, а не
по первому суточному расписанию: до него новый месяц мог бы уже начаться, и
первые записи ушли бы в `_default`.

### Сроки в месяцах

Месячная партиция удаляется целиком, поэтому срок в днях округляется вверх до
целых месяцев: `ceil(days / 30)`. Дополнительно действует
`storm.db.partition-min-keep-months` (по умолчанию 1) — страховка от
неверной настройки, при которой журнал лишился бы данных за вчера. Партиция
уходит, только когда выполнены оба условия: её месяц целиком старше срока
этой таблицы **и** прошло не меньше указанного числа месяцев.

Границы партиций считаются по UTC: `created_at` хранится в UTC, а отображаемое
время проекта — Europe/Minsk (ADR-016). Смена зоны сдвинула бы границы месяцев
на несколько часов, и часть строк попадала бы не в тот месяц.

## Чего чистка не делает

- Не удаляет `request_log` вместе с сессией: аудит живёт 30 дней независимо.
- Не трогает `stats_source_hourly` в пределах 3 месяцев — по ним считаются
  сравнения «вчера/неделю назад».
- Не чистит кэш «по времени жизни источника» принудительно: источник сам
  задаёт `expires_at`, максимум — `stale`.

## Проверки

- `RetentionCleanupTest` — проход удаляет только истёкшее, уважает лимиты и
  повторяем.
- `RetentionServiceTest` — бюджет операторов на 5 000 строк, `SKIP LOCKED`
  против занятой чужой транзакцией строки, добор после `DROP` партиции, у
  каждого журнала свой срок, запись ровно на границе срока остаётся.
- `MigrationCountTest` — `storm.db.expected-migrations` совпадает с числом
  файлов `V*.sql`: рассинхрон не роняет сборку, а тихо уводит приложение в
  503 в бою.
- `PartitionMaintenanceTest` — имя партиции совпадает с месяцем `createdAt`
  (сверяется по `tableoid`), новая партиция наследует автовакуум V4, месяц
  удаляется по своему журналу, округление дней идёт вверх, месяц считается по
  UTC.
- `MonthBoundaryTest` — записи на стыке месяцев не теряются, retention режет
  по границе месяца, агрегаты по часам не смешиваются.
- `IndexUsageTest` — чистка идёт по индексам, а не по последовательному
  сканированию.
- `SchemaConstraintTest.everyPartitionedTableHasDefaultPartition` — партиция
  «слепого месяца» не исчезла при следующей миграции.
